## Что просил владелец

«Надо сделать удобный интерфейс для поиска клиентов, поиска заказов клиентов и переход на страницу
заказа. Ну, то есть смешанный app, переход в другой app, получается. И нужно как бы поиск по телефону,
то, что делается в админке с клиентами, и вот это все. Пока что предварительно накидай план, как это
удобнее всего будет сделать».

## Идея

Оператору звонят. Он набирает четыре последние цифры номера, видит человека, видит его заказы,
открывает нужный и отвечает, что с ним происходит. По пути — три разных перехода:

1. по экранам одного приложения: поиск → карточка клиента → его заказы → карточка заказа;
2. **в другое приложение сервера**: карточка заказа → «Заказы», где у заказа есть кнопки статусов
   (это и есть «смешанный app» владельца);
3. позже — в нативное: карточка клиента → POS, «сделать заказ за него» (`order-entry.plan.md`).

Делать их тремя механизмами не надо. Механизм один: **у записи может быть ссылка, куда она ведёт** —
`_open`, ровно как у записи уже есть `_actions`. Строит её **сервер**: он один знает права и точки, и
ссылки, которой человек не может воспользоваться, в ответе просто нет — приложение не показывает
дверь, которая не откроется. Клиент получает **стек экранов**: один и тот же универсальный рендер
открывает по ссылке список, карточку или другое приложение, и ничего про «клиентов» и «заказы» не
знает.

Это дешевле, чем кажется, и нужно не только здесь: стек экранов и ссылки на записях — то, что
`data-query-layer.plan.md` всё равно потребует для связей между моделями, а переход в другое
приложение — то, чем POS будет открываться из карточки клиента.

**Главное решение владельца (Q30): карточка заказа не требует точки.** Заказ отдаётся по id — «просто
по API получить заказ без переключения точки». То есть основной путь целиком внутри «Клиентов»: заказ
любой точки открывается и читается, и ничья текущая точка от этого не меняется. Переход в «Заказы»
остаётся, но только там, где он ничего не переключает — когда заказ на точке, которая у человека уже
выбрана; иначе он идёт в «Заказы» сам, руками, как и сегодня. Механизм ссылок от этого не меняется:
он всё равно нужен для экранов внутри приложения и для POS.

## Что есть сейчас — факты

### Сервер: «Клиенты» уже написаны, но карточка — тупик

`apps/clients.ts` (не закоммичен): приложение `clients`, `scope: "server"`, права — модельные токены
adminizer (`read-customer-model`, `create-customer-model`), три метода:

| Метод | `ui` | Что отдаёт |
|---|---|---|
| `clients.list {q, cursor}` | `list`, `search: "q"`, `open: "clients.get"` | имя / телефон · заказов |
| `clients.get {id}` | `detail` | контакты, `addresses: string[]`, `orders: string[]` |
| `clients.create {name, phone, email?}` | `action` + `control: form` | `AuthService.materializeUser` |

Поиск уже сделан правильно: цифры (от трёх) ищутся в `AuthIdentity` (`provider: "phone"`,
`externalId` — нормализованные цифры), буквы — в `firstName` / `lastName` / `email`
(`adapters/clients.ts:71–96`). `user.phone` — json и, по комментарию модели (`models/User.ts:60–66`),
устаревшая проекция; искать по нему нельзя.

**Чего нет.** Заказы на карточке — массив строк («№1234 · 2026-05-12 · 1200 · DONE»,
`adapters/clients.ts:orderLine`). Это текст: нажать нельзя, перейти некуда, десять последних и всё.
Ровно то место, которое просит владелец.

### Сервер: «Заказы» — по точкам, и это мешает

`apps/orders.ts` (не закоммичен): приложение `orders`, `scope: "place"`, точки — из контекстного
токена `order-kanban`, плюс пункт «Без кухни». `orders.get` отдаёт заказ **только если им ведёт
текущая точка** (`adapters/orders.ts:ofPlace`). Значит:

- заказы одного клиента могут быть на разных точках, и список «его заказы» в приложении по точкам
  не живёт в принципе;
- заказ может быть на точке, которой у оператора нет (`order-kanban` контекстный) — переход в
  «Заказы» для него невозможен, а посмотреть заказ ему можно: на это есть `read-order-model`;
- заказ доставки без решённой кухни ведёт `no-kitchen` (`lib/order/orders-of-place.ts:orderPlaceId`
  возвращает `null`) — переход возможен только у того, у кого есть этот пункт токена.

### Клиент: два экрана, и переходов нет

`:render` — `ServerAppInstance` (374 строки): **домашний экран плюс одна карточка**, открытая из
списка. `open()` берёт метод из `home?.ui?.open?.let { app?.method(it) }`
(`ServerAppInstance.kt:273`) — то есть только метод **этого же** приложения, и только с одним
параметром `id`. Карточка (`Screens.kt:372` `RecordCard`) рисует заголовок, бейдж, действия и поля по
секциям; вложенных списков, ссылок и второго уровня нет. Формат `ref` в контракте есть и показывается
текстом (`Values.kt:60`) — не нажимается. `form` и действия `ui.on: "list"` («+») рендер пока не
рисует вовсе.

Сеть у приложения — `RestoServer`; `ServerSession.call` пропускает **только методы этого
приложения** (`ServerSession.kt:168–172`), токен и точку подставляет сам. Точка — **одна на сервер**,
общая для всех его приложений по точкам (`ServerSession.kt:225`, `lastPlace`).

### Superizer: переход между приложениями есть, стека нет

- `NavigationService.openApp(id, config)` (`core/.../runtime/Services.kt:137`): вежливо закрывает
  текущее приложение (может и отказать — `Vetoed`), запускает другое с его конфигом
  (`host/.../SuperizerHost.kt:872`). Открыто всегда одно приложение (D4), **снимок закрытого
  сохраняется** (`AppHandler.kt:297`) и возвращается в `restore()` при следующем запуске.
- `AppResult.payload` зарезервирован под «открыть X и получить значение» — пока всегда null.
- `deepLink` в манифесте есть, но он про внешние URL через `activation.fromDeepLink`, не про переход
  изнутри; для нашей задачи он не нужен.
- Оболочка **не читает `AppChrome.canGoBack`**: верхняя «<» закрывает приложение, поэтому «назад»
  приложение рисует само (так и сделано в карточке — `server-apps-and-rights.plan.md`, «Клиент», п. 10).

Вывод: переход между приложениями делается **без единой правки Superizer**. Возврат — тоже, за счёт
снимка: `saveState` «Клиентов» уже хранит id открытой карточки (`ServerAppInstance.kt:131`), и после
возврата карточка открывается снова.

### core: телефон заказа не ищется, пока заказ не выполнен

- `Order.user` ставится **только при `DONE`**: `doFinalize` заводит гостю аккаунт через
  `AuthService.materializeUser` и записывает `user` в заказ (`models/Order.ts:2529–2547`).
  Значит у активных гостевых заказов (`ORDER`, `COOKING`, `ON_THE_WAY`) `user` пустой — а это ровно
  те заказы, про которые звонят.
- Телефон такого заказа есть только в `Order.customer` — **json** (`models/Order.ts:230`). Искать по
  нему нельзя ни в Waterline, ни в глобальном поиске админки.
- Заказы точки читаются выборкой целиком и фильтруются в памяти, колонки точки у заказа нет
  (`lib/order/orders-of-place.ts`, лимит `ORDERS_OF_PLACE_MAX = 2000`).
- `AuthIdentity.externalId` — нормализованные цифры, уникален в паре с `provider` на уровне БД
  (`models/AuthIdentity.ts:19–42`). Это единственная по-настоящему искомая форма телефона.

### «Как в админке» — а в админке этого нет

Владелец сказал «поиск по телефону, то, что делается в админке с клиентами». Проверил: глобальный
поиск списка adminizer ищет только по полям типа `string`, `text` и `ref`
(`node_modules/adminizer/lib/list-query-builder/ListQueryBuilder.js:540–562`; `date`/`datetime`
исключены осознанно). У «Customers» телефон — json (`phone`), а `primaryPhone` — ссылка на
`AuthIdentity`, то есть `ref` на **uuid**, а не на цифры. **Найти клиента по телефону в вебе сейчас
нельзя.** То есть образца в админке нет: образец — наш поиск через `AuthIdentity`, и его стоит
принести в веб отдельной задачей (C15).

## Как ищется телефон — одно поле на всё

Оператор печатает в одно поле что попало: «5566», «+7 905 …», «8905…», «Иванов», «1234» (номер
заказа). Правила:

| Что ввели | Где ищем |
|---|---|
| ≥ 4 цифр | хвост номера: `AuthIdentity.externalId contains <цифры>` (`provider: "phone"`) → их `user` |
| ≥ 4 цифр | и номер заказа: `Order.shortId contains <цифры>` — он `string`, ищется напрямую |
| буквы | `firstName` / `lastName` / `email` клиента |
| смешанное | цифры из строки — как цифры, остальное — как буквы |

Почему хвост, а не «нормализовать и сравнить»: `8 905…` и `+7 905…` — один номер, `normalizePhone`
даёт `8905…` и `7905…` (`lib/AuthService.ts:210`), а `phoneFromDigits` сводит русскую национальную
форму к коду 7 (`lib/AuthService.ts:233`). Поиск по хвосту это переживает без правил по странам, а
короткий ввод («5566») для оператора — главный способ: он слышит номер по телефону, а не видит его.
Нижний порог — 4 цифры (3 даёт мусор на любой базе), лимит ответа — те же 200 строк, что сейчас.

Отдельная мелочь: `adapters/clients.ts:create` разбирает введённый номер через `lib/phone.splitPhone`
— эвристика «первая цифра — код страны». Для `+375…` она даёт код «3», а валидатор `User.phone`
такой код отвергает (об этом прямо написано в `lib/AuthService.ts:227–232`). Нужен публичный
`AuthService.parsePhone` (C16); пока его нет — заводить клиента можно только с номером, который
проходит словарь.

## Что добавляется в контракт — две ссылки, и всё

`protocolVersion` остаётся 1: поля необязательные, старый клиент их игнорирует и ведёт себя как
сейчас, старый сервер их не присылает.

```json
"open": { "type": "object", "required": ["method"], "additionalProperties": false,
          "properties": {
            "app":    { "$ref": "#/definitions/id" },
            "method": { "$ref": "#/definitions/methodName" },
            "params": { "type": "object" },
            "place":  { "type": "string" },
            "title":  { "$ref": "#/definitions/text" }
          } }
```

- **`_open` у записи** (рядом с `_actions`) — куда ведёт нажатие на строку или на карточку.
  Без `app` — метод этого же приложения (как `ui.open` сейчас, но с любыми параметрами, а не только
  `id`). С `app` — другое приложение; `place` обязателен, если оно по точкам.
- **`_links` у записи-карточки** — `[{title, meta?, open}]`: строки «куда дальше» внизу карточки,
  «Заказы · 12 →», «Адреса · 3 →», «Сделать заказ →». Это те же ссылки, только их рисует карточка, а
  не список.

Правила, которые важнее самих полей:

1. **Ссылку строит только сервер и только после проверки прав.** В хуке уже есть `isAvailable`,
   `availableApps`, `placesFor` (`lib/access.ts`, `lib/describe.ts`) — поверх них нужен один помощник
   контекста, `ctx.canOpen(method, placeId?)`. Нет права, нет точки, нет приложения — нет `_open`.
2. **Ссылка — не право.** Клиент по ней просто зовёт метод, и вызов проверяется как любой другой
   (`lib/call.ts`, `checkPermission`). Подделанный `_open` не даёт ничего.
3. `ui.open` остаётся — это ссылка «по умолчанию» для однородного списка; `_open` у записи её
   перебивает. Смешанные списки (клиенты и заказы в одном) станут возможны, когда у строки появится
   `_model` для форматирования, — это срез D, не сейчас.

## Методы сервера

Все — в приложении `clients` (`scope: "server"`, без точки), права — модельные токены adminizer.

| Метод | Доступ | `ui` | Что делает |
|---|---|---|---|
| `clients.list {q, cursor}` | `read-user-model`¹ | `list`, `search`, `open` | как сейчас, плюс поиск по хвосту номера от 4 цифр и `_links`-строка «Заказ №…», если `q` похож на номер заказа |
| `clients.get {id}` | то же | `detail` | контакты как сейчас; `addresses` остаются текстом; `orders: string[]` **убирается**, вместо него `_links`: «Заказы · N», «Сделать заказ» (когда есть POS) |
| `clients.orders {clientId?, q?, tab?, cursor?}` | `read-user-model` + `read-order-model` | `list`, `chips: tab`, `search: q` | заказы одного человека (`clientId`) или поиск заказов (`q`) среди точек оператора; строки: «№1234», «Доставка · Ленина 5», сумма, бейдж статуса, точка; у каждой — `_open` |
| `clients.order {id}` | `read-order-model` | `detail` | карточка заказа **только для чтения и без точки** (Q30): те же поля модели `order`, что в «Заказах», плюс строка «Точка: …»; `_links` — «Открыть в «Заказы»» только тогда, когда это ничего не переключит (ниже) |

¹ Модельные токены adminizer для ресурса «Customers» — это `read-customer-model`
(`apps/clients.ts` поясняет, почему именно так), в таблице сокращено.

Куда ведёт `_open` строки заказа — по решению Q30 всегда внутрь «Клиентов»:

```
есть read-order-model  →  {method: "clients.order", params: {id}}
иначе                  →  ссылки нет (и заказа в списке тоже нет)
```

А ссылка в «Заказы» — только на карточке заказа, и только когда переключать нечего: заказ ведёт та
точка, которая у человека **уже выбрана**, и у него есть `order-kanban` на неё. Тогда
`_links` получает строку «Открыть в «Заказы»» → `{app: "orders", method: "orders.get", params: {id}}`.
Заказ другой точки такой ссылки не получает: карточка на чтение у него есть, а менять точку сервера
за человека мы не будем.

**Поля модели `order` — один модуль на два приложения.** Сейчас список полей живёт в
`apps/orders.ts` (`models.order.fields`). Карточке в «Клиентах» нужен тот же — значит, он переезжает
в `lib/fields/order.ts` и подключается обоими приложениями. Иначе две карточки одного заказа
разойдутся с первой правкой, как разошлись бы коды отказа из C8.

**Чего сервер делать не должен.** Заказов в корзине (`NEW`, `CART`, `CHECKOUT`) в этих списках нет:
это недособранная корзина, а не заказ (так же решает `orders-of-place.ts`). Черновики POS — забота
POS.

## Экраны: что видит оператор

1. **Поиск** (home «Клиентов») — одно поле, строки «Имя · телефон · N заказов». Пусто — подсказка
   «Введите 4 цифры номера, имя или номер заказа».
2. **Карточка клиента** — контакты, адреса; внизу строки-ссылки: «Заказы · 12 →», «Сделать заказ →».
3. **Заказы клиента** — обычный список рендера: чипы «Активные / Все», сумма, бейдж статуса, точка.
4. **Карточка заказа (чтение)** — состав, суммы, адрес, точка, статус. Если можно — строка-ссылка
   «Открыть в «Заказы» →».
5. **«Заказы»** — то же приложение, что и так есть, открытое **на точке этого заказа** и сразу на его
   карточке: там кнопки «Готовить», «Отправить», «Выполнен», «Отклонить» и «Назначить кухню». Вверху
   своя строка «← К клиенту».

Все пять — один и тот же рендер; «Заказы» — тот же `ServerApp`. Нового экрана не рисуется ни одного.

## Что добавляется в клиенте

Переход в другое приложение, по шагам: `openApp(AppId("orders"), config)` → Superizer вежливо
закрывает «Клиентов» (их снимок с открытой карточкой сохраняется) → «Заказы» запускаются с
`target = {method: "orders.get", params: {id}, place: …, returnTo: "clients"}` → на первом кадре
`selectPlace(place)`, затем кадр карточки → «← К клиенту» зовёт `openApp(AppId("clients"))`, и снимок
возвращает ту же карточку клиента (она перечитывается с сервера — так же, как после перезапуска).

Если `openApp` отказал (`Vetoed`, `UnknownApp`, права изменились) — остаёмся на карточке чтения и
показываем одну строку: «Заказ ведёт точка «…», её нет в ваших правах». Ошибка перехода не должна
выглядеть как пустой экран.

## Точка: почему заказ отдаётся по id, без неё

Решение Q30. Точка у сервера одна и общая для всех его приложений по точкам
(`ServerSession.kt:225`), поэтому любой переход в «Заказы» за чужим заказом переключал бы её — и
«Блюда» после этого открывались бы на другой точке. Владелец: «просто пусть покажет заказ, не надо
переключаться — просто по API получить заказ без переключения точки».

Как это устроено в хуке:

- `clients.order {id}` — метод приложения `clients`, а оно `scope: "server"`: **точка в вызове не
  участвует вообще**, ни на входе, ни в проверке. Право одно — `read-order-model`.
- Точка заказа в ответе есть, но как **текст в поле** («Точка: Мира, 40»), а не как контекст работы.
  Считается она тем же `orderPlaceId` core (`lib/order/orders-of-place.ts`), что и в «Заказах», так
  что названия не разойдутся.
- «Заказы» не меняются ни на строку: они остаются приложением по точкам, с одной точкой за раз
  (решение Q18 основного плана — «всё по точкам, без смешивания»). Мы не просверливаем в них дыру,
  а отвечаем на вопрос «что с заказом» другим приложением, у которого точки нет.

Что это значит на практике: оператор видит и читает любой заказ любой точки, но **действовать**
(менять статус, назначать кухню) по-прежнему можно только в «Заказах» и только на своей точке —
туда он переключается сам, когда ему это действительно нужно.

## Аккаунт гостя: за настройками, по умолчанию — как сейчас

Решения Q32 и Q36. Владелец: «так же, как на сайте, но аккаунт делать по телефону, потому что этот
номер проверил курьер — в этом была логика; как создавать аккаунт, если номер не проверен — тогда
ставить галочку, что проверен только после доставки». И затем: «да, только доставку — и то это надо
перевести на настройку, и по умолчанию как сейчас поведение».

**Как сейчас.** Аккаунт гостю заводится при `DONE`, через `AuthService.materializeUser`
(`models/Order.ts:2529–2547`); телефонная идентичность создаётся **без доказательства**, и `verified`
остаётся `false` — это сделано осознанно: «номер был вписан в форму заказа, никто ничего не
доказывал». Важно, что `verified` вообще никто не пишет руками: это **проекция** доказательства
основной идентичности — `verified = Boolean(primary?.proof)` (`lib/AuthService.ts:1926`), и прежняя
версия core, которая ставила его при доставке напрямую, была из core убрана (комментарий там же).

**Что делаем — две настройки, обе выключены по умолчанию.** Описываются файлами в `core/settings/`,
как остальные (`settings/allow_user_without_phone.json` — образец: `key`, `type`, `defaultValue`), и
читаются через `Settings.get`, как `ALLOW_USER_WITHOUT_PHONE` и `REQUIRE_AUTH_FOR_CART`:

| Настройка | Выключена (по умолчанию) | Включена |
|---|---|---|
| `CREATE_ACCOUNT_ON_ORDER` | аккаунт заводится при `DONE` — ровно как сегодня | аккаунт заводится при оформлении (`Order.order`), тем же `materializeUser`, без доказательства: `verified` остаётся `false` — это и есть «галочка: номер не проверен» |
| `DELIVERY_PROVES_PHONE` | доставка ничего не подтверждает, `verified` остаётся `false` — как сегодня | при `DONE` **только доставки** (`serviceType === "delivery"`, Q36) на телефонную идентичность пишется доказательство `{at, method: "delivery", adapter: "core", purpose: "order-delivered"}` (форма уже есть — `AuthIdentityProof`, `models/AuthIdentity.ts:8`), и `verified` становится `true` **сам**, через `syncUserProjections`. Правило «`verified` руками не пишут» не нарушается |

Самовывоз и зал не подтверждают номер ни при какой настройке: человек пришёл сам, по номеру ему никто
не звонил (Q36, вариант 1).

В приложении и в админке состояние показывается словами: «подтверждён кодом» / «подтверждён
доставкой» / «не подтверждён» — оператор по телефону должен понимать, с кем говорит. Это работает при
любой настройке, просто при выключенных вариантов меньше.

**Чем это важно для поиска.** По умолчанию поведение остаётся сегодняшним, а значит у активного
заказа гостя по-прежнему нет ни аккаунта, ни искомого телефона. Поэтому **C13 возвращается в
обязательные**: колонка `Order.customerPhone` (нормализованные цифры, индекс) — единственный способ
найти по телефону активный заказ в конфигурации по умолчанию. С `CREATE_ACCOUNT_ON_ORDER` она
становится страховкой, без неё — основным путём. Делаем и то и другое: поиск должен работать
одинаково при любых настройках, а оператор про них знать не должен.

**Что надо знать перед тем, как включать на сервере.**

- `DELIVERY_PROVES_PHONE` делает «проверен» двусмысленным: «прошёл код» и «курьер довёз». Для входа
  это не открывает ничего — вход всё равно требует кода, а код настоящего владельца номера
  перезаписывает доказательство и забирает аккаунт себе (`lib/AuthService.ts:1443–1449`). Но если
  бонусные программы или рассылки где-то читают `verified` как «прошёл код», это надо проверить по
  модулям сервера, а не считать безопасным по умолчанию.
- `CREATE_ACCOUNT_ON_ORDER` заводит профиль у **каждого оформленного** заказа, включая отменённые и
  неоплаченные: клиентов в базе станет заметно больше, и событие `core:user-after-create`
  (`models/User.ts:223`), на которое могут быть подписаны приветственные бонусы и уведомления,
  начнёт срабатывать раньше, чем человек получил заказ.
- Опечатка в номере = заказ в профиле чужого человека. Так и сегодня (при `DONE`), но с включённой
  настройкой это случается раньше. Защита — ровно та галочка: до доставки аккаунт помечен «не
  подтверждён», и так он и показывается.
- Старым заказам аккаунты задним числом не заводим (Q37).

## Этапы — вертикальные срезы

**Срез A. Заказы клиента внутри «Клиентов».** Сервер: `clients.orders` (только с `clientId`),
`clients.order`, поля модели `order` в общий модуль, `_open` и `_links` в контракте и в хуке,
`ctx.canOpen`, поиск по хвосту номера от 4 цифр, `AuthService.parsePhone` (C16). Клиент: стек
экранов, `_open` у строки, `_links` на карточке, своё «назад»; демо-сервер получает «Клиентов» с
двумя людьми, чьи заказы — те же, что в демо-«Заказах». Готово, когда: оператор находит человека по
четырём цифрам, видит его заказы списком, открывает заказ и читает его — **включая заказ на точке,
которой у него нет**; у человека без `read-order-model` заказов на карточке нет; снимок возвращает тот
же кадр после перезапуска.

**Срез B. Переход в «Заказы» и обратно.** `_open` с `app`, `ServerAppConfig.target` и `returnTo`,
`openApp`, отказ перехода строкой. **Без переключения точки** (Q30): ссылка показывается только у
заказа той точки, которая уже выбрана. Готово, когда: оператор на точке А из карточки заказа этой же
точки попадает в «Заказы» сразу на его карточку, меняет статус и возвращается «К клиенту» на ту же
карточку; у заказа точки Б ссылки нет, а карточка чтения есть, и текущая точка нигде не менялась;
тест — через окно, на демо-сервере, и живой против хука (`tools/fake-server`).

**Срез C. Поиск заказов, а не только клиентов.** C13 (колонка телефона у заказа), C14 и C17 (две
настройки, выключенные); `clients.orders {q}` — поиск по номеру заказа и по телефону, чипы «Активные /
Все»; в `clients.list` — строка-ссылка на заказ, когда ввели номер; состояние номера («не подтверждён»
/ «подтверждён доставкой» / «подтверждён кодом») видно в карточке клиента и в карточке заказа. Готово,
когда: **при настройках по умолчанию** по телефону находится активный заказ человека, который заказал
впервые и аккаунт себе не заводил (через C13); с `CREATE_ACCOUNT_ON_ORDER` тот же заказ находится и
через аккаунт, и попадает в историю клиента сразу; с `DELIVERY_PROVES_PHONE` после доставки номер
становится подтверждённым, а после самовывоза — нет; по номеру заказа находится заказ; заказ любой
точки открывается на чтение. Тесты — обе конфигурации настроек, а не только включённая.

**Срез D. Удобства.** Смешанный список (клиенты и заказы в одном ответе, `_model` у строки),
«Сделать заказ» из карточки клиента в POS (`order-entry.plan.md`, срез A), последние искомые
клиенты, звонок по номеру с устройства (`openUrl("tel:…")`), настоящий стек приложений в Superizer
вместо `returnTo`.

Тесты на каждом срезе — как сейчас: хук на фальшивых `deps` и на поднятом Sails с админкой, клиент на
демо-сервере, живой прогон против хука и `RealServerWalkTest` через окно.

## Что сознательно не делаем в v1

- **Правка клиента с телефона** (имя, почта, телефон). Чтение и создание — да, правка — отдельный
  разговор: телефон в core — это идентичность, менять его мимо `AuthService` нельзя (Q34).
- **Слияние дублей.** Два профиля на одного человека бывают (аккаунт и гость с другим номером);
  склейка — задача core, не экрана.
- **Корзины** (`NEW`/`CART`/`CHECKOUT`) в списках заказов.
- **Бонусы, история звонков, заметки о клиенте.** Это CRM, её в плане нет.
- **Смешанный список** и форматирование строк разных моделей — срез D.

## Риски

- **Два поведения вместо одного.** C17 — это настройки, и значит у core появляются две конфигурации,
  которые надо держать в тестах обе: заказ без аккаунта (по умолчанию) и с аккаунтом с оформления.
  Приложение при этом должно выглядеть одинаково — на то и C13, чтобы поиск не зависел от настройки.
  Включение `CREATE_ACCOUNT_ON_ORDER` на живом сервере трогает не экран, а core и модули (клиентов
  станет больше, `core:user-after-create` раньше) — это отдельное эксплуатационное решение.
- **Поиск активного заказа гостя появляется только в срезе C.** В срезах A и B видны заказы клиентов
  с аккаунтом; «где мой заказ» от нового человека сработает после C13. На приёмке A и B этого ждать
  не надо.
- **Одно приложение за раз (D4).** Переход закрывает «Клиентов». Снимок возвращает карточку, но
  перечитывает её с сервера: на плохой связи возврат — экран с ошибкой и «Повторить». Настоящий стек
  — изменение Superizer, и его лучше делать осознанно (срез D), а не ради этой задачи.
- **Поиск с лимитом 200.** На большой базе «Иванов» не покажет всех. Пока терпимо; правильный ответ —
  keyset-курсор и поиск на стороне БД, то есть `data-query-layer.plan.md`.
- **Ссылки как канал прав.** `_open` — подсказка, а не разрешение; проверка остаётся на вызове. Это
  надо держать в тестах: вызов `orders.get` с подделанной точкой должен давать `place_forbidden`
  (такой тест уже есть).
- **Соблазн «дать действия прямо в «Клиентах»».** Карточка заказа там только для чтения, и так и
  должно остаться: иначе право по точкам (`order-kanban`) обойдено приложением без точек, а решение
  Q18 основного плана — «всё по точкам, без смешивания». Если действия по телефону понадобятся — это
  отдельное решение и отдельное право, а не строчка в этом плане.

### Q30. Переход в «Заказы» переключает текущую точку сервера. Так и оставить?

**Ответ владельца: вариант 3 — не переключать.** «Просто пусть покажет заказ, не надо
переключаться — просто по API получить заказ без переключения точки». Как это сделано — раздел
«Точка: почему заказ отдаётся по id, без неё». Ссылка в «Заказы» осталась только там, где
переключать нечего: у заказа уже выбранной точки.

**Что происходит.** Точка у сервера одна и общая для всех его приложений по точкам
(`ServerSession.kt:225`): какую выбрал в «Заказах», ту же покажут «Блюда». Оператор Аня сидит на
точке «Ленина, 5». Ей звонит гость, Аня находит его, видит заказ, который ведёт кухня «Мира, 40», и
нажимает «Открыть в «Заказы»». Приложение «Заказы» откроется **на точке «Мира, 40»** — иначе оно этот
заказ просто не покажет. Дальше Аня возвращается к клиенту, закрывает «Клиентов», открывает «Блюда» —
и там тоже «Мира, 40», пока она сама не переключит точку обратно.

| Вариант | Что увидит человек | Чего стоит |
|---|---|---|
| **1. Оставить так (рекомендация)** | точка меняется, и видно это сразу: она написана в подзаголовке приложения | ничего: механизм уже такой |
| 2. Вернуть прежнюю точку, когда он уйдёт с карточки заказа | «Блюда» остаются на «Ленина, 5» | понятие «точка на время одного экрана» вместо «точка сервера»; если из карточки заказа уйти сразу в «Блюда», непонятно, какая точка в силе — и остатки будут показаны не той точки, которую человек держит в голове |
| 3. Не переключать вовсе | перехода в «Заказы» нет, остаётся карточка заказа только для чтения | оператор не сможет вести чужой заказ даже там, где право есть; это фактически ответ «нет» на всю вторую половину задачи |

**Рекомендую 1**: человек в этот момент и правда занимается заказом этой точки, а точка подписана на
экране. Если боитесь путаницы — к варианту 1 можно добавить одно уведомление при переходе:
«Точка переключена на «Мира, 40»». Скажите, нужно ли.

### Q31. Заказ на точке, которой у оператора нет: показывать или нет?

**Ответ владельца: вариант 1 — показывать.** «Показывать: значит, у него есть права смотреть
заказы пользователей». То есть право `read-order-model` и есть разрешение видеть заказы клиента —
любой точки, на чтение.

**Что происходит.** Прав два разных. `read-order-model` — «можно читать заказы» (в вебе это же право
даёт список заказов целиком в админке). `order-kanban` — контекстный, с галочками точек: «этими
точками можно управлять». У Ани `order-kanban` только на «Ленина, 5», а читать заказы можно все. У
клиента в истории три заказа: два с «Ленина, 5» и один с «Мира, 40».

| Вариант | Что увидит Аня | Последствия |
|---|---|---|
| **1. Показывать все три, чужой — только для чтения (рекомендация)** | всю историю; у заказа с «Мира, 40» нет кнопок статусов и нет ссылки «Открыть в «Заказы»» | совпадает с вебом: там модельное право показывает все заказы, а доской по точкам управляет `order-kanban`. Оператор может ответить «ваш заказ готовится», но не может его тронуть |
| 2. Не показывать чужие заказы вовсе | историю клиента не целиком — только заказы её точек | на вопрос «где мой заказ» Аня ответит «у меня его не видно», и для гостя это звучит как потеря заказа. Плюс цифра «заказов: 7» на карточке не сойдётся со списком |
| 3. Показывать строкой, но не открывать | «№1234 · 12.05 · Мира, 40» без подробностей | история полная, состав и статус недоступны; половина звонков всё равно не обслуживается |

**Рекомендую 1.** Тут важно понимать: это решение про **право читать**, а не про право работать.
Если нужно, чтобы оператор видел только свои точки — это не галочка в приложении, а то, что нельзя
давать ему `read-order-model`; тогда заказов на карточке клиента у него не будет совсем.

### Q32. Как найти заказ гостя, у которого нет аккаунта?

**Ответ владельца: вариант 2, с галочкой.** «Так же, как на сайте, но аккаунт делать по телефону,
потому что этот номер проверил курьер — в этом была логика; как создавать аккаунт, если номер не
проверен — тогда ставить галочку, что проверен только после доставки». То есть аккаунт заводится при
оформлении и помечен «не подтверждён», а подтверждением считается доставка. Как это ложится на core
(`verified` — проекция доказательства, писать его руками нельзя) и чего стоит — раздел «Аккаунт
гостя», задача C17. **Уточнено ответом на Q36: это поведение — за настройкой, и по умолчанию
выключено**, то есть сегодняшний порядок (аккаунт при доставке) остаётся умолчанием, а колонка
телефона у заказа (C13) нужна обязательно — иначе при настройках по умолчанию активный заказ гостя не
находится.

**Что происходит.** Гость заказал с сайта, аккаунт не заводил. Пока заказ не доставлен, его телефон
лежит **только** внутри json-поля `Order.customer` (`models/Order.ts:230`), а связь с клиентом
(`Order.user`) ставится лишь при `DONE` — когда core заводит гостю аккаунт (`models/Order.ts:2529`).
По json база искать не умеет. То есть **самый частый звонок — «где мой заказ, телефон такой-то» —
сейчас не обслуживается никак**: заказ есть, но найти его по телефону невозможно.

| Вариант | Что даёт | Чего стоит |
|---|---|---|
| **1. Колонка телефона у заказа (C13, рекомендация)** | `Order.customerPhone` — те же цифры, но обычной строкой с индексом; заполняется при оформлении, старые заказы — миграцией. Поиск по телефону находит и активные гостевые заказы. Бонусом глобальный поиск админки начнёт находить заказ по телефону — строки он искать умеет, json нет | небольшая задача в core: поле, запись в двух местах, миграция. Поведение системы не меняется |
| 2. Заводить гостю аккаунт сразу при оформлении, а не при доставке | «заказы клиента» полны сами собой, новой колонки не надо | меняет поведение **всей** системы, не только приложения: профиль появится у каждого оформленного заказа — в том числе отменённого и неоплаченного. В «Клиентах» станет заметно больше людей, и бонусы, рассылки и RMS увидят их раньше, чем человек стал покупателем |
| 3. Ничего не делать | дешевле всего | по телефону находятся только клиенты с аккаунтом и их выполненные заказы. Активный заказ гостя — нет. Это надо принять заранее, а не на приёмке |

**Рекомендую 1.** Варианты 1 и 2 не исключают друг друга: колонку можно сделать сейчас, а решение
про ранний аккаунт принять отдельно — оно про учёт клиентов, а не про поиск.

### Q36. Что считать подтверждением номера, кроме кода?

**Ответ владельца: вариант 1, и всё новое поведение — за настройкой.** «Да, только доставку — и то
это надо перевести на настройку, и по умолчанию как сейчас поведение». Значит две настройки
(`CREATE_ACCOUNT_ON_ORDER`, `DELIVERY_PROVES_PHONE`), обе выключены, сегодняшнее поведение — умолчание;
подтверждает только доставка. Раздел «Аккаунт гостя», задача C17.

Из ответа на Q32: доставка подтверждает номер — курьер по нему звонил и передал заказ. А самовывоз и
зал? Там человек пришёл сам, и номер его никто не набирал: заказ выполнен, но про телефон это ничего
не говорит.

| Вариант | Что получится |
|---|---|
| **1. Подтверждает только доставка (рекомендация)** | честно: «подтверждён» значит, что по номеру дозвонились. У самовывоза и зала аккаунт остаётся «не подтверждён», пока человек не войдёт по коду |
| 2. Подтверждает любой выполненный заказ | проще объяснить оператору («заказ получен — номер верный»), но у самовывоза это неправда: номер мог быть любой |
