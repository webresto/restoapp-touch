## Что просил владелец

«У нас есть в сервере настройка каналов продаж… нужно продумать два плана. Первый — настройка по
каналам продаж, второй — управление маркетплейсом, установка и удаление программ через приложение. И
сделать центральный для администраторов пункт управления системными настройками, где будут сеттинги,
установка-удаление программ, кнопка перезагрузки сервера и кнопка настройки каналов продаж. **Всё по
аналогии с сервером**, UI проработать как в админке. Это нативные приложения, которые шлют в сервер
по аналогии с админкой. Доступно только администратору — или так, как это задумано в админке сейчас.
Мне нужен только план, код не править.»

## Идея

Канал продаж — это **один бекенд-клиент, который умеет создать заказ**: сайт, бот в мессенджере,
киоск, касса персонала. В сервере это два разных мира: *типы* каналов живут в памяти
(`SalesChannelRegistry`, 14 типов), а *настроенные экземпляры* — строки `SalesChannel`. И главное
правило, из-за которого страница устроена именно так: **канал существует только вместе со своим
модулем-провайдером**. Оператор ставит провайдера из маркетплейса, модуль на старте объявляет себя
живым, его канал появляется выключенным со статусом «нужна настройка», оператор дописывает настройки
на странице провайдера и только тогда включает канал.

Поэтому «Каналы продаж» на телефоне — это не CRUD по табличке. Это экран, который должен уметь
сказать **почему канал не работает** и **что сделать дальше**: поставить провайдера (а это уже
«Система», `system.plan.md`), дописать настройку у провайдера, включить переключатель. Ровно это и
делает веб-страница; весь её смысл в объяснениях, а не в полях.

Хорошая новость: все правила уже вынесены в `lib/SalesChannelProviders.ts` и работают сразу для трёх
потребителей — страницы админки, MCP-инструментов и чек-листа установки. Мобильный API становится
четвёртым, и **ни одного правила переписывать не надо** — надо только перестать копировать «вид»
записи (C29).

### Что такое канал — модель

`core/models/SalesChannel.ts`:

| Поле | Кто пишет | Что значит |
|---|---|---|
| `id` | core | uuid |
| `key` | оператор (слаг от названия) | стабильный id клиента; попадает в `Order.orderedOnPlatform` |
| `title` | оператор | «Основной сайт», «Бот доставки» |
| `type` | задаётся при создании и **больше не меняется** | слаг типа из реестра |
| `providerModule` | core из типа | `appId` модуля-провайдера; `null` у ручного канала |
| `managedBy` | core | `provider` — канал создал модуль, `operator` — руками |
| `enabled` | **оператор** | выключатель; сам по себе ничего не значит |
| `status` | **только провайдер** | `ready` / `needs_setup` / `error` (+ `draft`, `disabled` у старых строк) |
| `countries`, `concepts`, `platforms` | оператор | ISO-коды; список концепций (пусто = все); значения `orderedOnPlatform`, которые ведут в этот канал |
| `defaultConcept`, `allowConceptSwitch` | оператор | концепция по умолчанию и можно ли её менять на фронте |
| `url` | оператор | публичная ссылка/диплинк |
| `settings`, `publicConfig` | оператор | несекретная конфигурация; `publicConfig` отдаётся фронтам |
| `secretsRef` | **провайдер** | ссылки на секреты, не сами секреты; **в UI не отдаётся никогда** |
| `sortOrder` | оператор | порядок в списке |

Производные понятия, которые и рисует страница (`lib/SalesChannelProviders.ts`):

- **installed** — строка `Module` провайдера есть, не удалена и не выключена; `null` значит «модели
  `Module` нет» (минимальная установка), и это **не** повод что-то запрещать;
- **alive** — провайдер зарегистрировал адаптер в этом процессе (`SalesChannel.alive`);
- **active** — `enabled` + `status === "ready"` + alive. Только активный канал принимает заказы
  (`SalesChannel.resolve`), считается в чек-листе установки и в виджете.

Правила записи (`checkCanCreate`, `checkPlatforms`, `checkCanEnable`, `checkCanDelete`) — одни на
админку, MCP и чек-лист:

1. создать канал можно только для типа, который доступен (`!comingSoon && providerModule`) и чей
   провайдер **жив**; `supportsMultipleInstances: false` — только один канал типа;
2. `type`, `providerModule`, `managedBy`, `status` из тела запроса не берутся никогда;
3. включить можно только если провайдер **сейчас** отвечает `ready` — иначе 409 «Finish setup
   first» со ссылкой на настройки провайдера и его собственным сообщением;
4. платформа принадлежит одному каналу; проверяются только **добавленные** в этой записи платформы;
5. канал провайдера нельзя удалить, пока модуль установлен — только выключить; при удалении модуля
   core сам решает, что снести, а что оставить выключенным (`removeProviderChannels`);
6. `key` уникален (проверяется в контроллере, уникального индекса в базе нет), слаг транслитерует
   кириллицу (`slugify` в `sales-channels-helpers.ts`, и та же функция продублирована на клиенте
   страницы и в MCP).

### Чек-лист страницы — «один в один»

Это ТЗ. Каждый пункт — то, что должно оказаться на телефоне (`src/sales-channels-manager.jsx`).

1. **Карточки каналов**, по `sortOrder ASC`: иконка типа, название, под ним `key · тип`
   моноширинным, справа **бейдж статуса** с точкой: Working / Needs setup / Draft / Disabled /
   Error (`statusLabel`, `STATUS_COLORS`).
2. **Сообщение провайдера** под карточкой, если он его дал и жив (`statusMessage`).
3. **Плашка «провайдера нет»** (`ProviderMissingNotice`) с тремя разными текстами: «тип скоро», «не
   работает: провайдер не установлен (appId)», «провайдер не загрузился: перезапустите сервер», и
   кнопкой «Установить провайдера» — только при праве `modules-process-upgrade`.
4. **Чипсы-бейджи** на карточке: концепции (или «Все концепции»), страны, платформы.
5. **Переключатель** «Включён / Выключен»: заблокирован, когда провайдер не жив, и показывает
   выключенным, не меняя записи. Без права `manage` — просто слово.
6. **Отказ 409 остаётся на карточке** до следующего переключения: текст отказа, под ним сообщение
   провайдера (`toggleRefusal`).
7. **Кнопки карточки**: «Настроить» (если провайдер жив и статус не `ready`) или «Настройки» (если
   `ready`) — обе ведут на `settingsUrl?channel=<id>` провайдера; «Открыть» (внешний `url` канала);
   «Изменить»; «Удалить» (только когда `canDelete`).
8. **Удаление — с вопросом** (`ConfirmDialog`): «Удалить «название»? Существующие заказы сохранят
   свой источник для отчётов».
9. **Редактор** (`ChannelEditor`) полями: Название, Ключ канала (слаг, подсказка «стабильный id,
   пишется в orderedOnPlatform»), Тип (**заблокирован у существующего**), URL, Страны (ISO через
   запятую), Платформы (через запятую, с подсказкой), блок «Привязка к концепции» —
   мультивыбор концепций, концепция по умолчанию, переключатель «разрешить переключение», и
   переключатель «Включён» (у нового канала его нет: «канал создаётся выключенным»).
10. **Ключ выводится из названия** слагом, пока оператор не правил его руками; подсказка «ключ
    обязателен» появляется только после того, как название введено.
11. **Отказ сервера в редакторе** — плашкой над полями, не только тостом.
12. **Раздел «Рекомендуем для <страна>»** — типы по стране проекта, кроме тех, канал которых уже
    есть; у каждого — «Установить из маркетплейса» или «Поискать в маркетплейсе» (по тегу
    `sales-channel:<тип>`), или «Coming soon».
13. **Кнопка «Все каналы продаж в маркетплейсе»** в заголовке — каталог по тегу `sales-channel`.
14. **Отдельный экран «Свой канал»** (`?view=custom`): все 14 типов карточками, и «Создать канал»
    там, где провайдер жив; «Только один канал этого типа», когда нельзя. Канал, созданный там,
    управляется с главного экрана.
15. **Пустое состояние**: иконка, «Каналов продаж пока нет», «Каналы появляются, когда вы
    устанавливаете модуль-провайдер из маркетплейса — выберите рекомендованный ниже».
16. **Свежесть статуса**: список спрашивает провайдеров **на каждом чтении**
    (`refreshStatuses` → `channelStatus` → `getStatus` с таймаутом 3 с на канал), поэтому
    «собрался фронт» видно сразу.
17. **Два уровня права** в одном экране: `canView` рисует всё, `canManage` добавляет кнопки, а
    `settingsUrl`, `providerModule` и `settings` вообще не отдаются тому, у кого нет `manage`
    (`mapChannel` в `sales-channels-helpers.ts`).
18. **Узкий экран** — `useIsMobile()`: одна колонка карточек и кнопки на всю ширину. То есть
    мобильная раскладка этой страницы уже придумана.

### Хук: чего в нём нет

- Приложения «Каналы» нет. О `SalesChannel` хук не знает ничего; POS пишет заказы с
  `orderedOnPlatform: "mobile-pos"` (`adapters/pos.ts:65`) — и это **платформа без канала** (C33).
- Переход в другое приложение в контракте **уже есть**: `open: {app, method, params, place}`
  (`schema/declaration.schema.json`, `definitions/open`), и клиент его умеет
  (`ServerAppInstance.openLink` → `runtime.navigation.openApp`). Значит «Установить провайдера»
  честно ведёт в «Систему», а не в никуда.
- Чего в контракте нет — **внешней ссылки**: ни `link`, ни `open` не умеют `url`. А `settingsUrl`
  провайдера и страница модуля в маркетплейсе — это именно веб-адреса (Q53).
- Переводятся только значения ключей `title`, `category`, `empty`, `confirm`, `section`
  (`lib/i18n.ts:8`). Тексты отказов — английские фразы, которые служат ключами i18n админки
  (`refusalText`), и их надо перевести **на сервере**, в сообщение ошибки (C31).

### Клиент (ветка `main`): что уже умеет и чего не хватает

Умеет и переиспользуется как есть: список с поиском, чипсами и группировкой; карточка записи полями
по секциям и строками-ссылками `_links`; стек экранов; `control: {type: "toggle"}` и

(`NativeActions`, `NativeActionScope` с `record`, `call`, `submit`, `close`); **переход в другое
приложение** по ссылке (`openLink`, `Open.app`).

Чего нет:

| Чего нет | Где видно |
|---|---|
| Формы по схеме: `FormField` знает `string`/`integer`/`number`/`boolean` и `enum` чипсами; массивы и объекты выбрасываются | `Components.kt:505`, `Screens.kt:722` |
| Предзаполнения формы существующим значением | `Components.kt:526` (`FormCard`) |

| Отрисовки отказа сервера на нативном экране | `Screens.kt:112–130`, `ServerAppInstance.kt:565` |

Всё это — та же работа, что уже расписана в `settings.plan.md` (срезы B и C): схемный редактор в
`:render`, шторка с поиском, `NativeActionScope.failure`. **Каналы берут её готовой и ничего из неё
не дублируют** — поэтому срез «редактор канала» идёт после среза B «Настроек».

## Решение: список и карточка декларацией, редактор — нативным экраном (Q51)

Одно приложение `channels`, `scope: "server"`, иконка-витрина (`storefront`), категория «Система»
(та же, что у «Настроек» и «Системы»).

- **Список каналов и карточка канала — декларацией.** Поиск по названию/ключу/типу, чипсы
  «Все / Работают / Выключены / Нужна настройка», бейдж статуса, секции карточки, ссылки — всё это
  универсальный рендер уже рисует.
- **Редактор канала — нативный экран** `channel-editor`: мультивыбор концепций, страны, платформы,
  слаг из названия, блокировка типа — декларацией это не описать, а экран, получающий запись и
  отдающий параметры, описать можно (тот же приём, что у редактора акции и редактора настройки).
- **Каталог типов — второй список** (`channels.types`), ровно как «Свой канал» в вебе: карточки
  типов с одним действием каждая. Рекомендации по стране — чипс «Рекомендуем» в том же списке, а не
  третий экран.
- **«Установить провайдера» — ссылка в «Систему»**: `open: {app: "system", method: "system.catalog",
  params: {appId}}`, и она появляется только если `ctx.canOpen` сказал «этот человек туда может»
  (то есть у него есть `modules-process-upgrade`). «Все каналы продаж в маркетплейсе» — та же ссылка
  с `params: {tags: "sales-channel"}`.
- **«Настроить» у провайдера — внешняя ссылка** (Q53): `settingsUrl` — это страница админки модуля,
  нативного экрана для неё нет и быть не может. По умолчанию — открываем в браузере системы.
- **Права — токены веба**: `anyOf: [sales-channels-manager, sales-channels-view,
  sales-channels-manage]` на чтение, `anyOf: [sales-channels-manager, sales-channels-manage]` на
  запись (Q52). Правило D8 «доступ в админку = доступ в приложение» сохраняется, и два уровня права
  работают сами: у кого нет `manage`, у того `describeItem` не вернёт действий, а `settingsUrl` и
  `settings` не приедут в записи.
- **Статусы спрашиваем дорого и редко** (C32): список отдаёт сохранённый `status`, карточка —
  свежий. `since` в `channels.list` **не объявляем** — значит клиент этот список не опрашивает
  (`ServerAppInstance.startPolling` включается только при наличии `since`), и провайдеров никто не
  дёргает каждые десять секунд.

## Модель и методы

Модель `channel` (поля, которые объявляются рендеру):

| Поле | Формат | Что в нём |
|---|---|---|
| `title` | `text` | заголовок строки и карточки |
| `subtitle` | `text` | `key · typeTitle` — как в вебе, одной строкой |
| `statusText` | `enum` + `x-titles` + `specials` | «Работает» / «Нужна настройка» / «Ошибка» / «Выключен» / «Черновик» — бейдж строки, тон из `specials` |
| `statusMessage` | `text` | что сказал провайдер (уже переведённое, C31) |
| `providerText` | `text` | «Провайдер: admin-frontend · установлен» / «не установлен» / «не загрузился» / «тип скоро» |
| `enabledText` | `boolean` | выключатель оператора отдельно от готовности |
| `conceptsText`, `countriesText`, `platformsText` | `text` | списки через `·`; пусто = «Все концепции» |
| `url` | `text`, секция «Ссылки» | публичный адрес канала |
| `typeTitle`, `category`, `capabilities` | `text`, секция «Тип» | из реестра |
| `updatedAt` | `relative` | когда правили |

Почему `statusText`/`providerText` строками, а не «настоящими» полями: у строки списка в контракте
**один** бейдж, а объяснение «почему не работает» в вебе собирается из четырёх флагов
(`providerInstalled`, `providerAlive`, `typeComingSoon`, `status`). Слова эти сервер и так знает —
он их знает и для веба; значит слова считает он (C29), а флаги едут рядом, для нативного экрана и
для `describeItem`.

Методы:

| Метод | Вид | `input` | `ui` | Что делает |
|---|---|---|---|---|
| `channels.list` | query | `{q, state}` | `view: list`, `item: {title, subtitle, meta: providerText, badge: statusText}`, `search: q`, `chips: state`, `open: channels.get`, `empty` | каналы по `sortOrder ASC`, поиск как в вебе (`title`/`key`/`type`/`typeTitle`), `state` — `all\|active\|off\|needs_setup\|error`; **сохранённый** статус |
| `channels.get` | query | `{id}` | `view: detail` | один канал: поля модели + `enabled`, `status`, `statusMessage`, `providerInstalled`, `providerAlive`, `typeComingSoon`, `marketplaceAppId`, `settingsUrl`, `canDelete`, `concepts`, `countries`, `platforms`, `defaultConcept`, `allowConceptSwitch`, `conceptOptions`, `typeOptions`; статус — **свежий** (`channelStatus`) |
| `channels.toggle` | mutation | `{id, enabled}` | `view: action`, `on: channel`, `placement: [row, detail]`, `control: {type: toggle, param: enabled, bind: enabledText}` | выключатель; отказ 409 приходит как `conflict` с человеческим текстом и сообщением провайдера; `describeItem` снимает действие, когда провайдер не жив или нет `manage` |
| `channels.save` | mutation | `{id?, key, title, type?, url, countries[], platforms[], concepts[], defaultConcept, allowConceptSwitch}` | `view: action`, `on: channel`, `placement: [detail]`, `control: {type: native, screen: channel-editor}` | создать или сохранить; правила — C30 |
| `channels.delete` | mutation | `{id}` | `view: action`, `on: channel`, `placement: [detail]`, `control: {type: buttons}`, `confirm` | удалить; `describeItem` — `false`, когда `canDelete` ложно |
| `channels.types` | query | `{kind}` | `view: list`, `item: {title, subtitle: stateText, badge: availability}`, `chips: kind` (`recommended\|all`), `open: channels.type` | каталог 14 типов + рекомендации по `COUNTRY_ISO`; `recommended` — по умолчанию |
| `channels.type` | query | `{id}` | `view: detail` | карточка типа: название, категория, возможности, провайдер, состояние, ссылки «Установить провайдера» / «Поискать в маркетплейсе» (обе — в «Систему») |
| `channels.create` | mutation | те же поля, что `save`, плюс `type` обязателен | `view: action`, `on: type`, `placement: [detail]`, `control: {type: native, screen: channel-editor}` | «Создать канал» с карточки типа; `describeItem` — `false`, если тип недоступен, провайдер не жив или `supportsMultipleInstances` исчерпан, и тогда в `statusText` типа видно, почему |

Записи дают `id` канала (uuid) и `id` типа (слаг). Ссылка `restoapp://app/channels/<id>` —
мобильный аналог адреса карточки в вебе.

Что пишется в журнал (`audit`): `channels.toggle` — `{id, enabled}`; `channels.save`/`create` — все
поля, кроме `settings` и `publicConfig` (их мобильный редактор не правит, Q55); `channels.delete` —
`{id, key}`. `secretsRef` в журнал, в список и в карточку не попадает никогда — как и в вебе.

## Статус реализации

На 2026-11-04 сделаны срезы **A, B и C** и задачи **C29–C32**. Ветки: клиент `channels-apps`, сервер
`channels-api`, core `channels-core`; сервер и core не запушены. **D** (редактор, `channels.save`,
`channels.create`) и **E** (`restoapp://app/channels/<id>`, C33 «Касса») не начаты. Q51–Q56 по-прежнему
открыты: в коде стоят рекомендации плана.

Что сделано не буквально по плану:

- **Строка «Типы каналов» и «Все каналы продаж в маркетплейсе» — последняя строка списка** со своим
  `_open`, потому что у ответа-списка нет `_links`, а новых ключей в контракт, кроме `open: {url}`, не
  добавляем. Строка есть только на всём списке: под фильтром и поиском она скрыла бы пустое состояние.
  При нуле каналов она объясняет, откуда они берутся (пункт 15 чек-листа).
- **`open: {url}` — ровно один из `method` и `url`** (`oneOf`), адрес — http(s) или путь, и клиент сам
  отказывает во всём остальном: браузер системы открывается со слов сервера. Строку «Открыть» для адреса,
  который телефон не откроет (`example.org` без схемы), сервер не строит.
- **Переход в другое приложение теперь несёт цель.** Раньше `openLink` звал `openApp(id)` и терял метод с
  параметрами, поэтому «Установить провайдера» открыла бы «Систему» на главном экране. Теперь цель едет в
  `ServerAppConfig.target` и открывается поверх стека приложения; метод, которого у человека нет, — фраза
  словами, а не пустой экран. Заодно исправлено: отказ `openApp` приходит как `Result` и раньше молча терялся.
- **Поле, которого в записи нет, не рисуется и в строке списка**, а не только в карточке: иначе `—` стояло
  плашкой-бейджем и хвостом подзаголовка. Значение `null` по-прежнему `—`.
- **«Установить провайдера» требует и `ctx.canOpen("system.catalog")`, и `modules-process-upgrade`**: как
  кнопка страницы. «Искать в маркетплейсе» — только `canOpen`, как и там.
- **«Что делать»** — поле карточки со второй строкой `ProviderMissingNotice`; в таблице полей его не было,
  а на странице эта строка видна и без кнопки установки.

Что ждёт «Систему»: `system.catalog` должен принимать `{appId}` и `{tags}`. Пока метода на сервере нет,
ссылок в «Систему» нет ни у кого, и это проверено тестом; с заглушкой метода тест видит и ссылки, и их
параметры, но настоящего перехода в каталог ещё никто не проходил.

Что расходится со страницей и оставлено: категория и возможности на карточке — словами реестра, по-английски
(`messenger`, `orders:create`; на странице их нет вовсе, в план они вошли); плашка «Скоро появится» у типа
видна и читателю (на странице её показывает блок действий, скрытый без `manage`).

## Что добавляется в контракт

Одно необязательное расширение, которое нужно не только здесь:

- **`open: {url}`** — строка-ссылка ведёт на внешний адрес, а не на метод (Q53). Клиенту есть чем
  это сделать: `runtime.navigation.openUrl` (`superizer/core/.../Services.kt:145`) есть на всех
  платформах. Нужно каналам («Настроить» у провайдера, «Открыть» сайт канала), «Системе» (страница
  модуля в маркетплейсе) и когда-нибудь любому «открой это в вебе». Правило то же, что у `app`:
  клиент, который ключа не знает, строку не рисует.

Больше ничего: нативный экран читает запись целиком, `toggle`, `buttons`, `confirm`, `chips` и
`_links` в контракте уже есть.

## Что нужно от core

- **C29. «Вид» канала — одной функцией.** `mapChannel` существует **дважды**:
  `lib/adminpanel/src/controller/sales-channels-helpers.ts` (для страницы) и
  `hook/mcp/sales-channels.ts` (для MCP) — почти одинаковые, с разным набором полей и разным
  отношением к правам. Мобильный API был бы третьей копией. Переносим в
  `lib/sales-channels/view.ts`: `describeChannel(channel, {canManage, installed, computed, t})`
  отдаёт и флаги, и **слова** (`statusText`, `providerText` — те самые, что сейчас собирает jsx), а
  контроллер и MCP становятся её потребителями. Тот же ход, что C24 для настроек.
- **C30. Правила записи — в `lib/`, а не в контроллере.** `checkCan*` уже в
  `lib/SalesChannelProviders.ts`, а вот уникальность `key`, слаг, «тип не меняется», «что из тела
  вообще можно взять» и «новый канал всегда выключен» живут в `upsert-sales-channel.ts`
  (и продублированы в MCP-инструменте). `applyChannel(body, {existing, t})` в
  `lib/sales-channels/apply.ts` — и веб, телефон и MCP пишут одинаково **по построению**.
- **C31. Отказ — человеческой фразой, а не ключом.** `SalesChannelRefusal.error` — английская
  фраза, которая служит ключом i18n админки (`refusalText(refusal, t)`), и у неё бывают
  `{placeholders}` и `extra.message` от провайдера. Хук переводит только пять ключей `ui`
  (`lib/i18n.ts:8`), поэтому текст отказа должен приходить **уже переведённым** в `message` ошибки
  `conflict`: `fail("conflict", refusalText(refusal, ctx.t))`, а `settingsUrl`/`marketplaceAppId`
  из `extra` — в `details`. Иначе телефон покажет «Finish setup first» человеку, читающему
  по-русски. Переводы этих фраз в `core/lib/adminpanel/i18n/locales/*.json` уже есть — нужен доступ
  к ним из хука (вернуть `t` через `ctx.t` + словарь core).
- **C32. Готовность канала — с кешем.** `channelStatus()` спрашивает провайдера на **каждом**
  чтении (таймаут 3 с на канал, `models/SalesChannel.ts:202`), а документация честно просит
  авторов провайдеров «кешируйте у себя». Веб это терпит: страница читается раз в открытие. Телефон
  читает карточку чаще и мог бы читать список по опросу. Нужен кеш в core — `refreshStatus` с
  окном в 5–10 секунд (как `CACHE_MS` фактов сервера в `adapters/sails.ts:36`), общий для веба,
  телефона, MCP и чек-листа. Без него телефон — ещё один повод дёргать чужие API.
- **C33. У POS нет канала, хотя заказы он пишет.** `adapters/pos.ts:65` ставит
  `orderedOnPlatform: "mobile-pos"`, тип `mobile-pos` в реестре есть и помечен «не coming soon» — а
  `isTypeAvailable()` требует `providerModule`, которого у него `null`. Значит тип показывается
  недоступным, канал создать нельзя, `SalesChannel.resolve("mobile-pos")` возвращает `null`, и
  заказы кассы не привязаны ни к одному каналу: ни в чек-листе, ни в виджете, ни в привязке к
  концепции их нет. Лечение — провайдером типа становится сам хук мобильного API: `SalesChannelAdapter`
  в `app-mobile-api`, который на старте зовёт `SalesChannel.alive(...)` и отвечает `ready`, когда
  `MOBILE_API_ENABLED`. Тогда «Касса» появляется на экране каналов сама, как и положено каналу.
  **Это ошибка и в вебе**, не только помеха телефону.

## Этапы — вертикальные срезы

**A. Раздел и чтение.** Сервер: `apps/channels.ts` + `adapters/channels.ts` на C29, методы
`channels.list` / `channels.get`, права двух уровней, слова в `locales/{ru,en}.json`.
Клиент: ничего нового. Проверяем: каналы видны, статус и «почему не работает» словами, поиск и
чипсы состояния работают, у человека без `manage` нет действий и нет `settingsUrl`.

**B. Выключатель и удаление.** Сервер: `channels.toggle`, `channels.delete`, `describeItem`,
человеческие отказы (C31). Клиент: ничего нового (`toggle`, `confirm` уже есть). Проверяем: канал
без живого провайдера не включается и объясняет, почему; канал провайдера не удаляется, пока модуль
установлен; отказ виден на карточке.

**C. Типы, рекомендации и переходы.** Сервер: `channels.types`, `channels.type`, ссылки в «Систему»
через `ctx.canOpen` (нужен срез A `system.plan.md`). Клиент: `open: {url}`, если берём Q53.
Проверяем: 14 типов, «Рекомендуем» по `COUNTRY_ISO`, «Установить провайдера» открывает каталог
«Системы» на нужном модуле.

**D. Редактор.** После среза B «Настроек» (там появляются схемный редактор, шторка с поиском и
`NativeActionScope.failure`). Сервер: `channels.save`, `channels.create` на C30. Клиент: модуль
`apps/channels`, экран `channel-editor`: слаг из названия, тип только для чтения у существующего,
мультивыбор концепций (из `conceptOptions`), страны и платформы списками с добавлением, вопрос про
несохранённые правки. Проверяем: создание канала с карточки типа, отказ по занятой платформе, отказ
по уникальности ключа.

**E. Мелочи.** `restoapp://app/channels/<id>`; «Касса» как настоящий канал (C33) — и её карточка на
этом же экране; кеш готовности (C32).

Как проверяем: хуку — `tests/mobile-api.channels.test.ts` на фальшивых `deps` (образец —
`mobile-api.marketing.test.ts`): права двух уровней, отказы правил, ссылки записи, `describeItem`.
Клиенту — экранные тесты на демо-сервере (`render/.../ServerAppTest.kt`,
`apps/marketing/.../PromotionEditorTest.kt`) плюс живой тест против настоящего хука
(`composeApp/.../LiveServerTest.kt`): войти, увидеть каналы стенда, включить канал и получить
отказ, открыть типы и перейти в каталог «Системы».

- **`settings` и `publicConfig` канала** — свободный JSON, который правит провайдер; в вебе их
  редактора тоже нет (Q55).
- **`secretsRef`** — не показываем и не правим никогда.
- **Создание типов каналов** — тип приносит модуль; руками типов не бывает.
- **Порядок каналов (`sortOrder`)** — в вебе его не меняют мышью, и мы не будем.
- **Виджет «сколько каналов работает»** — это дашборд админки; домашний экран «Системы» скажет то же
  словами.
- **Опрос списка каналов** — пока C32 не сделан, опрос означает «дёргать провайдеров каждые 10 с».

## Риски

- **Чужие API на каждом чтении** (C32): карточка канала = запрос к провайдеру, у которого 3 с
  таймаута. Два человека с телефонами и открытая страница в вебе — это уже заметная нагрузка на
  бота.
- **Статус «не загрузился» после установки**: провайдер появляется только после перезапуска
  сервера, то есть сценарий «поставил провайдера — включил канал» на телефоне неизбежно разрывается
  перезапуском (`system.plan.md`, и там же — что перезапуск в кластере сегодня чинит только одного
  воркера).
- **Платформа без канала** (C33): пока POS не канал, его заказы не считаются в чек-листе установки,
  и человек видит «нет работающих каналов продаж» на сервере, который принимает заказы с кассы.
- **Слаг в трёх местах** (`slugify` в helpers, в jsx, в MCP): телефон станет четвёртым, если не
  сделать C30. Расхождение проявляется ровно там, где его труднее всего заметить — у названий на
  языках вне charmap (CJK слагируется в пустую строку).
- **`key` без уникального индекса**: уникальность проверяется запросом перед записью, значит две
  одновременные записи (веб и телефон) могут создать два канала с одним ключом. Риск существует и
  сейчас; телефон делает его чуть вероятнее.
- **Удаление канала необратимо** (жёсткое `destroy`, мягкого удаления в модели нет) — подтверждение
  обязательно, и формулировка должна быть той же, что в вебе: заказы сохранят свой источник.

## Вопросы владельцу

### Q51. Нативное — всё приложение или только редактор?

Владелец сказал «это нативные приложения». В словаре этих планов «нативное» значит «клиент рисует
сам», в отличие от декларации.

**Рекомендую: нативным сделать редактор канала, остальное — декларацией.** Список, карточка, чипсы,
переключатель, подтверждение, ссылки и права уже написаны и ведут себя как во всех остальных
приложениях; нативным нужно то, чего декларацией не описать — мультивыбор концепций, страны,
платформы и слаг из названия. Если нужно именно двухпанельно, как в вебе на широком экране, — это
отдельный срез и целиком нативное приложение; скажите, и план перепишется.

### Q52. Кто пускается в «Каналы»?

**Рекомендую: токены веба и два уровня** — `sales-channels-view` открывает приложение,
`sales-channels-manage` даёт действия (плюс legacy `sales-channels-manager` как полный доступ, как в
`SALES_CHANNELS_ACCESS`). Администратор проходит и так. Отдельное «мобильное» право означало бы, что
человек, правящий каналы в вебе, с телефона их не видит. Строже — `isAdministrator` в декларации,
и тогда каналы на телефоне видит только администратор.

### Q53. Внешние ссылки на телефоне

«Настроить» у провайдера, «Открыть» сайт канала и страница модуля в маркетплейсе — это веб-адреса.

**Рекомендую: добавить в контракт `open: {url}` и открывать в браузере системы** (`openUrl` в
Superizer уже есть на всех платформах). Один ключ, польза сразу трём приложениям. Альтернативы:
(а) показывать адрес текстом, пусть копируют руками — честно, но неудобно; (б) встроенный веб-вид в
приложении — отдельная большая работа, и страница админки в нём потребует входа заново.

### Q54. Создание канала руками — нужно ли на телефоне?

В вебе это отдельный экран «Свой канал», и создать там можно только канал типа с живым провайдером
(то есть сегодня — только второй сайт).

**Рекомендую: делать, срезом D** — это тот же нативный экран, что и редактирование, плюс один
`describeItem`. Если на телефоне нужно только «смотреть и включать», срез D не делаем вовсе, и
приложение остаётся читающим с выключателем.

### Q55. `settings` и `publicConfig` канала

Это свободный JSON инстанса; в вебе редактора для них нет — их пишет провайдер.

**Рекомендую: как в вебе** — не показывать и не править. Когда схемный редактор из «Настроек»
будет готов, их можно будет открыть сырым JSON — но только если попросите: это конфигурация, которую
провайдер считает своей.

### Q56. «Касса» как канал продаж (C33)

Сегодня POS пишет `orderedOnPlatform: "mobile-pos"`, а канала с таким ключом создать нельзя.

**Рекомендую: починить в core — провайдером типа становится хук мобильного API**, и «Касса»
появляется на экране каналов как обычный канал (выключенный, пока `MOBILE_API_ENABLED` не включён).
Это небольшая правка и она закрывает дыру в чек-листе установки. Альтернатива — просто записать как
известную ошибку и не трогать в этом плане (как C26 в «Настройках»).
