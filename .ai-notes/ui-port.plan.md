> из них — архитектура изменений Superizer (раздел 7), работа начата с шага S1. Нумерация В/А — локальная, чтобы не пересекаться с Q/D README.
> Прототип: `../prototype-rikka/cloudApp`, коммит `a88827e` (репозиторий `prototype-rikka`, ветка
> `main`); скриншоты всех экранов — `../prototype-rikka/screenshots/cloud/{compact,medium,expanded}/`.
> Гайд, по которому он собран: `../superizer/docs/13-ui-guidelines.md` (черновик, ветка
> `docs/ui-kit-guide`). Факты о Superizer и клиенте сверены с кодом 2026-11-18.

## 1. Что такое прототип и чем он не похож на Superizer

Прототип — **одно** wasm-приложение со своей навигацией: два контекста (сервер ресторана `r/…` и
аккаунт Resto Cloud), в каждом список разделов, который рисуется нижней панелью (телефон), рельсом
(планшет) или сайдбаром (десктоп). Разделы — это просто экраны одного приложения, переход — смена
маршрута.

В Superizer всё иначе:

| | Прототип | Superizer + RestoApp touch сейчас |
|---|---|---|
| Раздел | экран одного приложения | **отдельное приложение** (`AppId`), сервер объявляет его в декларации протокола 1 |
| Переход между разделами | смена маршрута | `open(id)`: текущее приложение закрывается (снимок состояния), открывается другое; одно открытое за раз |
| Навигация | нижняя панель / рельс / сайдбар | **выдвижное меню** (`AppScaffold`): переключатель контекстов, «Главная», приложения с Home, «Все приложения», футер с настройками |
| Пункт меню | иконка, название, бейдж, группа | `MenuEntry(label, onClick, enabled, danger)` — только текст |
| Ширина | `Page` с `PageWidth` 720/1120/1360 dp | всё содержимое в колонке **480 dp** (`Capped`, `MaxContentWidth`, D36) |
| «Главная» | сводка дня (выручка, кухня, заказы) | сетка плиток приложений контекста (`HomeScreen`) |
| Точка | одна на весь сервер, в оболочке | у каждого приложения своя (`PlaceSwitch` рендера, `scope: place`) |
| «Назад» | вверх по маршруту, с подписью «‹ Заказы» | стрелка оболочки = `SystemBackHandler`; приложение считает свои шаги (`ScreenSteps`), подписи нет |
| Компоненты | `cloudApp/ui/kit` поверх `ui-kit` | `ui-kit` 0.10.0 + `render/Components.kt` клиента |

Вывод: **прототип переносится не экранами, а слоями.** Оболочка прототипа — это будущий
`SuperizerShell`, его разделы — приложения, а большинство экранов рисует не код экрана, а общий рендер
декларации.

## 2. Кто рисует каждый экран

Сейчас у клиента два способа нарисовать приложение (README, `order-entry.plan.md`):

- **рендер** (`render/`, ~4 300 строк): универсальный, по декларации — `Views.LIST` / `DETAIL` /
  `ACTION`, подсказки `ItemUi(title, subtitle, meta, value, badge, image)`, `chips`, `search`,
  `groupBy`, контролы `stepper` / `toggle` / `buttons` / `form` / `native`, стек кадров, ссылки
  записи, вопрос о несохранённом;
- **нативный экран** (`apps/*`): `client: {native: …}` у приложения или `control: native` у действия.

| Экран прототипа | Кто рисует | Чего не хватает, чтобы выглядело как в прототипе |
|---|---|---|
| Заказы — список, фильтр, поиск | рендер (`list`) | вид списка по ширине (карточки / таблица); **доска по этапам — нового вида нет** |
| Заказ — карточка | рендер (`detail`) | две колонки (`TwoColumn`), полоса этапов, главная кнопка «следующий этап» из `buttons` |
| Блюда / стоп-лист | рендер (`list` + `stepper` + `toggle` + `groupBy`) | только вид: всё нужное в протоколе уже есть |
| Блюдо | рендер (`detail`) | вид; доступность по точкам — как ссылки или вложенный список |
| Клиенты, клиент | рендер | вид; плитки статистики у записи — нового нет (см. `summary`) |
| Маркетинг: сводка | рендер (`detail` «сводка», `marketing.plan.md` Q40 — числами) | плитки KPI и графики — **нового вида нет** |
| Акции, промокоды, применения | рендер | вид; переключатель в карточке списка есть (`toggle` в `row`) |
| Редактор акции | **натив** (`apps/marketing`, 759 строк) | переписать на новые компоненты, превью «Так увидит гость» |
| Касса | **натив** (`apps/pos`, 2 222 строки) | раскладка «каталог + чек» на широком окне, новые шторки/диалоги |
| Ассистент | **натив** (`apps/assistant`, 1 634 строки) | список разговоров слева на десктопе, карточки инструментов |
| Настройки сервера | рендер (список) + натив (редактор значения, перенос) | вид списка; диалог правки и шторка экспорта/импорта — на новых компонентах |
| Программы, каналы продаж | рендер (`DemoSystemApps`) + натив прогресса (`apps/system`) | вид; таймлайн установки |
| Resto Cloud: сервисы, аккаунт/баланс | рендер (cloud-panel `layers/app-mobile-api` объявляет «Серверы», «Аккаунт») | вид; баланс-«герой», графики расхода — **`summary`** |
| Вход, подключение, создание сервиса | хост (`composeApp`, `ServerScreens.kt`) | переписать экраны хоста как сфокусированный сценарий (T7) |
| «Главная» сервера (сводка дня) | — сейчас нет | **решение В2** |
| ⌘K-поиск | — нет | оболочка; не первая очередь |

Итого: из ~30 экранов прототипа **~20 — это один рендер**, ~8 — нативные экраны, ~3 — хост. Когда
рендер научится новому виду, он сразу получат все серверы, включая cloud.

## 3. Что меняется по слоям

### 3.1. `ui-kit` (Superizer) — компоненты

Из `prototype-rikka/cloudApp/src/wasmJsMain/kotlin/cloud/ui/kit` (~1 240 строк) и частей экранов:

- оверлеи: `Dialog` (центр на широком, шторка на телефоне), `SideSheet`, `Menu`/`MenuItem`, `Select`,
  `ConfirmDialog` (с вводом имени), тост;
- страница: `Page(PageWidth)`, `PageHeader` (крошки, бейдж, мета, действия), `Panel`, `Grid`,
  `DataTable`/`Col`, `LineTabs`, `Chip`, `EmptyState` (две формы), `Stat`, `FactRow`, `CopyValue`;
- статус: `Tone`, `StatusBadge`/`Pill`, `StatusDot` — **словарь статусов остаётся в приложении**, в kit
  только тоны;
- графики: `Sparkline`, `BarChart`, `Ring`, `Meter`, `ShareBar`;
- из форков: `QtyStepper`, `FlowRow`, мультивыбор в диалоге, закреплённая нижняя панель действий,
  радио-выбор;
- окно: `WindowClass`, `LocalWindowClass`, `byWindow(…)`.

Цвета: в прототипе `CloudColors` (холст, бренд и его мягкая заливка, терминал, палитра графиков) —
добавить в `KitColors` (`canvas`, `brand`, `brandSoft`, `onBrandSoft`, `chart`…) светлый и тёмный
наборы. Фирменный фиолетовый — значения RestoApp, не Superizer: kit получает слоты, хост передаёт
значения (`KitTheme(colors = …)`). Типографика прототипа (на ступень плотнее) — так же, через
`kitTypography`.

Правила kit (12 §5): только добавлять, `api/*.api` — ревью контракта, тест на каждый компонент, без
сторонних типов в API.

### 3.2. `ui` (Superizer) — адаптивная оболочка

Главная работа и главный риск: `SuperizerShell` используют и другие хосты (Unitool, touch-vn,
app-learn).

- **Одно меню, три отрисовки** по ширине окна (гайд §1.2): телефон — выдвижное меню как сейчас (нижняя
  панель — только внутри приложения, В1); планшет — рельс из иконок; десктоп — постоянная боковая панель с переключателем
  контекста сверху и футером внизу. Источник один — то, что сейчас строит `menu` (`onHome` + «Все
  приложения»).
- `MenuEntry` → добавить `icon`, `group`, `badge` (через новый конструктор/поля с умолчаниями — ABI
  только растёт). Иконка уже есть у приложения (`AppMetadata.icon`, `category`), бейджа нет — см. 3.3.
- **Снять колонку 480 dp** для приложений, которые объявили, что умеют шире: флаг в манифесте или
  `AppMetadata` (`adaptive = true`), иначе `Capped` как сейчас. Так старые приложения и хосты не
  меняются.
- Подпись «‹ Заказы» у стрелки: `BackChain` сейчас знает только число шагов (`ScreenSteps`); добавить
  заголовок шага (`ScreenSteps(count, upTitle)`), иначе стрелка без подписи — терпимо.
- Шапка: сейчас заголовок бара — название приложения. На широком окне заголовок рисует `PageHeader`
  внутри страницы, бар оболочки исчезает (как в прототипе); на телефоне остаётся.
- Совместимость: включать адаптивность параметром `SuperizerShell(adaptive = true)`; по умолчанию —
  нынешнее поведение. RestoApp включает, остальные хосты — когда захотят.

### 3.3. `core` (Superizer) — немного API

- бейдж приложения: `StateFlow<String?>` от приложения (через `AppRuntime`, например
  `runtime.badge.set("8")`) — оболочка показывает в меню;
- признак «умеет шире 480» в метаданных (см. 3.2);
- ~~общая точка в `ContextPort`~~ — не нужна (В3 решён: точки свои у каждого приложения и
  пользователя).

### 3.4. Протокол 1 — новые подсказки (клиент **и** сервер)

Всё — **необязательные** ключи: старый клиент их не знает и рисует как сейчас (правило протокола:
незнакомое — текстом, не падение).

| Ключ | Зачем | Где на сервере |
|---|---|---|
| `ui.view: "board"` + `ui.columns` (поле статуса, порядок) | доска заказов | restoapp-dev `app-mobile-api`, приложение «Заказы» |
| `ui.view: "summary"` + блоки (`metric`, `series`, `list`, `share`) | сводка дня, маркетинг, баланс cloud | restoapp-dev, cloud-panel `layers/app-mobile-api` |
| `ui.columns` у `list` (какие поля в таблице на широком окне, выравнивание) | таблицы вместо строк | оба |
| `item.tone` / тоны статусов по значениям (`x-tones` рядом с `x-titles`) | `StatusBadge` из словаря | оба |
| `app.badge` (метод-счётчик или поле в декларации) | «Заказы · 8» в меню | restoapp-dev |
| `ui.primary` у действия | одна главная кнопка записи | оба |

Схема — `schema/declaration.schema.json` хука и контрактные тесты (`protocol/`), как раньше.

### 3.5. `render` (клиент) — новый вид

~4 300 строк; переписывается внешний вид, не логика кадров:

- `ListScreen`: карточки на телефоне, таблица по `ui.columns` на широком, `FilterBar` (поиск + чипы),
  скелетоны, `EmptyState` в двух формах; группы `groupBy` — секциями-панелями;
- `DetailScreen`/`RecordCard`: `PageHeader` (название, бейдж, мета, главное действие + `⋯`),
  `TwoColumn` (основное + рельс с фактами), ссылки записи — ссылками;
- новые виды `board` и `summary` (по 3.4);
- `Components.kt` рендера (`Group`, `ListRow`, `Badge`, `BottomSheet`, `ChoiceSheet`, `FormCard`…)
  заменяются компонентами kit, файл худеет;
- тоны: `toneOf` → `Tone` kit.

## 4. Этапы и оценка

Оценка — в днях сосредоточенной работы одного исполнителя, с тестами и скриншотами в трёх ширинах.
Разброс — честный: самое неопределённое — оболочка (чужие хосты) и сервер.

| # | Этап | Где | Дней | Зависит от |
|---|---|---|---|---|
| 1 | Компоненты и окно в `ui-kit` (3.1), галерея, тесты, ABI, доки 12/13 | superizer | 4–5 | — |
| 2 | Тема RestoApp: цвета, шрифт, `HostTheme` | superizer + composeApp | 1 | 1 |
| 3 | Адаптивная оболочка (3.2) за флагом, `MenuEntry` с иконкой/группой, снятие 480 по флагу приложения | superizer `ui` | 5–7 | 1 |

| 7 | Протокол: `board` и `summary` — клиент + серверы; «Главная» по В2 | все три | 5–7 | 6 |

## 5. Риски

- **Чужие хосты.** Изменения оболочки и kit — только добавлением и за флагом; ABI-дамп `api/*.api` —
  ревью. Unitool, touch-vn, app-learn до явного включения не меняются.
- **Протокол у двух серверов.** `board`/`summary` нужны и в restoapp-dev, и в cloud-panel; клиент
  обязан рисовать без них (старые серверы) — значит, до этапа 7 доска и сводки есть только как
  список и карточка.
- **wasm/desktop/iOS/Android.** Прототип проверен только в wasm. Оверлеи сделаны слоем в корневом
  `Box` (не системные окна) — на iOS/Android проверить клавиатуру, `safe area`, жест «назад» поверх
  шторки.
- **Тач и мышь.** Наведение в прототипе — украшение, но `pointerHoverIcon` и hover-заливка на iOS
  не работают — проверить, что ничего не держится только на них.
- **Плотность.** Типографика прототипа на ступень меньше kit (15/13 sp против 16/14) — на телефоне
  проверить читаемость, возможно, плотность по классу окна.
- **Логика в прототипе отсутствует.** Всё, что там «работает» (смена статуса, перезапуск, оплата), —
  в памяти; переносится только вид, поведение берётся из нынешних приложений.

## 6. Вопросы владельцу

- **В1. Нижняя панель на телефоне — решено:** «пусть будет панель внутри app, но не глобальная».
  Оболочка остаётся с выдвижным меню (на широком — рельс и боковая панель, 3.2); нижняя панель —
  **навигация внутри одного приложения** по его разделам (касса: чеки / каталог; маркетинг: сводка /
  акции / промокоды / применения). Нужен примитив разделов приложения (7.4), глобальной панели нет.
- **В2. «Главная» — решено:** «главная всего приложения будет как-то формироваться, но потом; пока
  просто показывать последнее состояние и открытый сервер». Сводка дня откладывается; при запуске
  открывается последний контекст и последнее открытое в нём приложение (7.6). Плитки Home остаются.
- **В3. Точки — решено:** точки продаж и приготовления у пользователя могут быть разными (у
  маркетолога — свои), у кого-то одна; это задают настройки пользователя на сервере. Значит, **одной
  точки на сервер в оболочке нет**: список точек приходит у каждого приложения своим
  (`DeclaredApp.places` уже по приложению), выбор — в приложении, в шапке страницы. Это работа клиента
  (рендер), не Superizer; `selection` в `ContextPort` не нужен. Клиент запоминает выбор по приложению,
  а приложение с тем же набором точек начинает с последнего выбора (удобство, не правило).
- **В4. Шире 480 dp — решено по рекомендации:** только у приложений, объявивших `AppWidth.Adaptive` (7.3).
- **В5. Фирменный цвет — решено:** «фиолетовый надо, чтобы можно было настраивать в настройках».
  Акцент — **настройка пользователя** в Settings хоста рядом с «Оформлением» (как `ThemeMode`):
  `HostSettingsPort.accent`, набор пресетов (фиолетовый по умолчанию у RestoApp, синий, зелёный,
  оранжевый, розовый, графит). Kit выводит из одного цвета акцента его производные в обеих темах
  (`primary`, `brand`, `brandSoft`, `onBrandSoft`, `ring`) — `kitColors(dark, accent)`. Хост задаёт
  акцент по умолчанию, пользователь меняет.
- **В6. Порядок — решено:** начать с архитектуры — сделать в Superizer всё, что нужно (раздел 7).
  Этапы 1, 3, 4 таблицы 4 идут первыми; работа в рендере и приложениях — после.

## 7. Архитектура изменений в Superizer

Всё — добавлением: `api/*.api` только растёт, умолчания дают нынешнее поведение, Unitool, touch-vn и
app-learn не меняются, пока сами не включат новое. Версия — **0.11.0**, ветка `adaptive` от
`origin/master` (2229798). Контракт (`SuperizerContract.VERSION`) не двигается: новое в `core` —
необязательные поля и методы с реализацией по умолчанию.

### 7.1. Окно — `ui-kit`

- `enum class WindowClass { Compact, Medium, Expanded }`, `LocalWindowClass`, `WindowClassProvider {}`
  (один `BoxWithConstraints` у корня), `byWindow(compact, medium, expanded)`.
- Границы — 600 и **1000 dp** (не 840: с боковой панелью 264 dp на 840 остаётся 576 dp — это нашёл
  прототип; гайд 13 §1.1 поправить).
- Класс — от ширины окна, не от платформы. Оболочка ставит провайдер сама; приложение под тестом —
  `FakeAppRuntime` даёт `Compact`, если не сказано иное.

### 7.2. Компоненты — `ui-kit`

Из прототипа (раздел 3.1): `Page`/`PageWidth`, `PageHeader`, `Panel`, `Grid`, `DataTable`, `LineTabs`,
`Chip`, `FilterBar`, `EmptyState`, `Stat`, `FactRow`, `CopyValue`, `Tone`/`StatusBadge`/`StatusDot`,
`Dialog`/`ConfirmDialog`/`SideSheet`/`Menu`/`Select`/`Toast`, `QtyStepper`, `FlowRow`, графики. Оверлеи —
через `Popup` (как в прототипе), а не системные окна: одинаково на четырёх платформах.

Цвета — новые слоты `KitColors` (`canvas`, `brand`, `brandSoft`, `onBrandSoft`, `chart`) в обоих наборах;
значения RestoApp передаёт хост (В5). Заодно закрыть известный пробел: `HostTheme` сбрасывает
типографику kit — `HostTheme(mode, colors?, typography?)`.

### 7.3. Что приложение говорит оболочке — `core`, `AppChrome`

`AppChrome` уже есть (`title`, `subtitle`, `canGoBack`, `fullscreen`) и меняется на лету — сюда же:

- `width: AppWidth = AppWidth.Capped` — `Capped` (480 dp, как сейчас) или `Adaptive` (оболочка не
  ограничивает, ширину держит `Page` приложения). Это и есть ответ на В4 «по объявлению».
- `upTitle: String? = null` — куда ведёт «назад» внутри приложения («Заказы»): подпись у стрелки и
  крошка в шапке.

Бейдж в меню виден и у закрытого приложения, поэтому он не в `AppChrome`, а в `setup`:

- `AppSetupContext.badge(flow: StateFlow<String?>)` — регистрируется в `setup`, живёт до disable,
  снимается диспозером. Реализация по умолчанию — ничего не делает (старые хосты).

### 7.4. Разделы внутри приложения (В1) — `ui`

Примитив для приложения, а не для оболочки:

```kotlin
AppSections(
    items = listOf(Section("receipts", "Чеки", Lucide.Receipt, badge = "3"), …),
    selected = "catalog",
    onSelect = { … },
) { /* содержимое выбранного раздела */ }
```

| Окно | Как рисуется |
|---|---|
| `Compact` | нижняя панель внутри области приложения (над safe area и клавиатурой), 3–5 разделов |
| `Medium`, `Expanded` | вкладки под шапкой страницы (`LineTabs`); боковая навигация — только оболочки |

Выбранный раздел — сохраняемое состояние приложения (его `saveState`), не маршрут оболочки.
Оболочка про разделы не знает. Рендер получит то же из декларации (вкладки = методы приложения с
`ui.section`, отдельный вопрос протокола, не Superizer).

### 7.5. Адаптивная оболочка — `ui`, `SuperizerShell`

- `SuperizerShell(…, layout: ShellLayout = ShellLayout.Drawer)`; `ShellLayout.Adaptive` включает:

| Окно | Меню | Верх |
|---|---|---|
| `Compact` | выдвижное, как сейчас | бар оболочки: «‹ upTitle» или ☰, заголовок |
| `Medium` | рельс 84 dp: значок контекста, приложения иконками, поиск/настройки внизу | бар оболочки |
| `Expanded` | боковая панель 264 dp: переключатель контекста, приложения с иконками и бейджами, группы по `category`, футер | у `Adaptive`-приложения бара нет — шапку рисует его `PageHeader`, «назад» — крошкой из `upTitle`; у `Capped` — бар как сейчас |

- Пункты меню строятся из того же, что сейчас (`onHome` + «Все приложения»); `MenuEntry` получает
  `icon: AppIcon?`, `group: String?`, `badge: String?`, `selected` (вторые конструкторы — ABI растёт).
- `AppIcon.Named` рисуется иконкой Lucide по имени (таблица имён в `ui`), `Letter` — монограммой.
- Переключатель контекстов (`ContextRow`) и футер — те же компоненты, на трёх раскладках.

**А1 — решено по рекомендации:** на `Expanded` у `Adaptive`-приложений бара оболочки нет; заголовок
рисует `PageHeader`, «назад» — крошкой из `upTitle`.

### 7.6. Запуск: последний контекст и последнее приложение (В2) — `core` + хост

- Сейчас `restoreLastSession` поднимает приложение со снимком не старше суток, а закрытие без
  `keepSnapshot` снимок стирает. Нужно разделить «что было открыто» и «его состояние»:
  `lastOpened` (id приложения и конфиг, без срока) и снимок состояния (как сейчас, 24 ч).
  При старте: снимок свежий — открыть с ним; старый — открыть то же приложение без него.
- Последний контекст — забота хоста: RestoApp запоминает выбранный сервер (`ContextPort.switchTo`
  при старте). У Superizer — только порядок: сначала контекст, потом приложение этого контекста;
  у каждого контекста свой `lastOpened` (хранилище по контексту уже отдельное).

**А2 — решено по рекомендации:** приложение, закрытое «назад» на Home, при следующем запуске не
открывается — открывается Home; `lastOpened` стирается при явном закрытии.
