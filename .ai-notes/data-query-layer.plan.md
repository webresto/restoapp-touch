# План: универсальный слой данных — запросы по `QueryCriteria` и автоэкраны

> Версия 1.2, 2026-11-03: вопросы Q1–Q3 закрыты владельцем; суммы убраны, остался подсчёт «всего».
> Делается **после первого релиза** `server-apps-and-rights.plan.md` (срез 4),
> тем же реестром `mobileApi` и тем же транспортом `describe` / `call`. Отдельный план — решение
> владельца; здесь собрано всё, что в версии 1 основного плана было разделом 5 и вопросом Q8, с
> поправками по коду adminizer 5.2 и sails-adminpanel.

## Что просил владелец

«Может сделать аналог GraphQL, чтобы можно было запросы собирать самому на основании того, что
[доступно], чтобы автогенератором делать; может есть проект попроще, чем gql, но тоже со схемой».
«А если нужен свой обработчик, которого нет в DataAccessor, например статичные хендлеры вообще без
базы — можно добавить?»

Ответы на вопросы плана (2026-11-03): права на поля галочками — «нет, пока не надо»; автоэкраны —
«по правам, у кого есть»; подсчёты и суммы в запросах — «да». Затем: «а зачем эти суммы нужны?» —
у сумм нет потребителя, поэтому остался только подсчёт «всего» у списка.

## Идея

Любая модель из конфига админки, на которую у человека есть `read`, автоматически получает в клиенте
список → карточку → форму — как веб-adminizer, с теми же правами, без кода на сервере и в клиенте.
Это **три встроенных метода** основного реестра, а не отдельный протокол:

| Метод | Аналог в GraphQL | Что |
|---|---|---|
| `data.schema` | интроспекция | Под пользователя: модели с `read`, видимые поля (тип, заголовок, `enum`, связь → модель), `ops` (`list / view / add / edit / remove` по токенам), поля для `edit` / `add`, поля для фильтра и сортировки. JSON Schema + `x-` ключи |
| `data.query {<имя>: {model, where, select, populate, sort, limit, skip, total}, …}` | query | Несколько именованных запросов за раз; `total: true` — сколько всего записей под этим отбором |
| `data.mutate {model, op: create\|update\|delete, id, data}` | mutation | DataAccessor `add / edit / remove` |

Свои обработчики без модели («статичные хендлеры») — это обычные методы основного реестра с
`access: {tokens | token | public}`; им отдельный план не нужен, они есть уже в срезе 1.

## Что есть в adminizer 5.2 и чего не хватает

- **Язык запросов есть**: `QueryCriteria` (`interfaces/queryCriteria.ts`) — `where` с `eq / ne / gt /
  gte / lt / lte / in / notIn / between / contains / startsWith / isNull`, `and / or / not`; `select`;
  вложенный `populate` со своими критериями; `sort`, `limit`, `skip`.
- **`model.find(criteria, dataAccessor)`** (`AbstractModel.ts`) добавляет `where` по записям и
  фильтрует поля **на выходе**. Ключи `where`, `sort`, `select` против видимых полей **не
  проверяются** — фильтр или сортировка по скрытому полю работает как оракул данных.
- **Адаптер `SailsORMAdapter.js` в sails-adminpanel портит критерии**: любой массив становится `{in}`
  (ломает `or` / `and`), `gt / gte / lt / lte / eq` не транслируются и уходят в Waterline как есть,
  объектный `select` выбрасывается, без `populate` подтягиваются все связи.
- В 5.2 нестроковый `sort` сворачивается в `where` (`DataAccessor.ts` ~866).

Вывод: на `model.find` полагаться нельзя. Хук пишет **свой транслятор** `QueryCriteria → Waterline`
и **свой валидатор**, а DataAccessor остаётся источником прав: `getFieldsConfig()` для видимых полей
и полей записи, `getRecordAccessWhere()` для записей.

## Дизайн

**Валидатор** (до транслятора, на любой глубине `populate`):
- `select`, ключи `where`, `sort` — только видимые поля модели; `populate` — только связи на
  модели с `read`; глубина `populate` ≤ 2; `limit` ≤ 100; именованных запросов ≤ 10 за вызов;
- операторы — белый список из `QueryCriteria`; `regex`, `jsonContains` и сырые объекты Waterline не
  принимаются ни от кого (администратору — через веб);
- **точки**: модели, данные которых живут по точкам (`Order`, `OrderDish`, `DishPlace`), в
  `data.schema` и `data.query` есть только с фильтром по текущей точке вызова — тем же правилом, что в
  основном плане (раздел 1, «Точки»); без правила для модели она в схему не попадает, чтобы generic
  запрос не смешал точки;
- `data.mutate` пишет только поля из `getFieldsConfig()` для `edit` / `add`; поля, которые ведёт
  действие, закрыты: `mobileApi.protectField('order', 'state', 'orders.setState')` — `order.state`
  пишется только через `orders.setState` и `Order.next`.

**Транслятор** — свой, по контракту `QueryCriteria`, а не через адаптер sails-adminpanel: `or / and /
not` → Waterline `or / and / !=`, `between` → `>= / <=`, `contains / startsWith` → `contains /
startsWith`, `isNull` → `null`, массив — только там, где это `in`. Контрактные тесты на каждый оператор
против sails-disk и Postgres.

**`data.schema`** строится из того же, что `GET /admin/model/:model/filter-fields` adminizer
(`filterFields.ts`): `getFieldsConfig()`, заголовки через i18n, `enum` из `isIn`. Связи там отдаются
только для Sequelize — для Waterline берём их из атрибутов модели сами. Кешируется по ревизии и языку,
как декларация.

**Автоэкраны в клиенте** — тот же `ServerApp` рендер: модель из `data.schema` → приложение «Данные»
с меню моделей → `list` по `data.query` → `detail` → форма по схеме `edit`. Меню — по тем же
токенам (`listAccessibleMenuItems` в adminizer нет; есть `menuHelper.getMenuItems(user)` без фильтра
и `InertiaMenuHelper` с фильтром, но только как проп Inertia — фильтруем сами по токенам).
Классы под схему не генерируем: схема своя у каждого пользователя и меняется вместе с правами. В
Kotlin — типизированный построитель `QueryCriteria` (`@Serializable`) и разбор ответа по схеме.
Если к этому времени появятся JS-приложения (`script-apps.plan.md`, D9), автоэкраны можно сделать
скриптом `auto.js` с сервера, а не кодом клиента, — решается там, Q3.

**Подсчёт «всего».** `total: true` у запроса списка добавляет в ответ число записей под тем же
отбором: тем же проверенным `where`, плюс `getRecordAccessWhere()` аксессора, плюс фильтр по текущей
точке для моделей по точкам. Это число в заголовке списка и «показано 50 из 230». Считает Waterline
`count` тем же критерием.
- Сумм, средних, минимума и максимума нет: у них нет потребителя. Сумма только по видимым записям
  разная у разных людей и вводит в заблуждение как отчёт.
- Плитки показателей («Выручка за сегодня», средний чек) — отдельными методами реестра по точке под
  галочкой отчётов (`orders-report`), как отчёты в вебе.

**Кому доступно** (владелец: «по правам, у кого есть»): приложение «Данные» видит каждый, у кого есть
чтение хотя бы одной модели из конфига админки; внутри — только эти модели и только разрешённые
операции. Отдельной галочки нет: мобильное получает ровно то, что веб, — у кого в вебе есть правка
модели, у того она будет и здесь. Группа `Stock Manager` из основного плана токенов моделей не
имеет, поэтому в «Данных» у неё пусто, и цену блюда она не меняет.

**«Заказы» и «Блюда» остаются пресетами**: их методы из основного плана — удобные виды поверх тех же
прав; генерик-экраны их не заменяют.

## Права на поля галочками (бывший Q8) — отложено

Владелец: «нет, пока не надо». В этапы не входит; ниже — заметка на будущее.

Сейчас поле ограничивается `groupsAccessRights: ['Group']` в конфиге модели — **список разрешённых
групп** по имени, без учёта регистра. Два следствия: поле с списком не видит никто, кроме
перечисленных, включая веб; переименовали группу — поле «отвалилось». Поэтому в основном плане
`groupsAccessRights` не используется.

Если нужны галочки «склад меняет только остаток и наличие», хук может вести поля сам:
- регистрирует токены `field-update-<model>-<field>` для полей, которые объявлены как «ведомые»;
- после каждого сохранения группы пересчитывает `groupsAccessRights` этих полей из токенов групп;
- на старте проверяет, что все упомянутые группы существуют, и пишет предупреждение в лог.
Это влияет и на веб-админку — DataAccessor один.

## Почему не GraphQL / OData / JSON:API / PostgREST

| Вариант | Плюсы | Почему не он |
|---|---|---|
| GraphQL | Запросы собирает клиент, есть схема | Схема своя у каждого пользователя; резолверы поверх DataAccessor; Apollo Kotlin генерирует код по постоянной схеме при сборке. В restoapp он есть, но для покупателей |
| OData v4 | Ближе всех: `$metadata` + `$select / $expand / $filter` | Большая спецификация, парсер `$filter`, тяжёлые клиенты |
| JSON:API | Простой, выбор полей и `include` | Нет схемы, фильтры не стандартизованы |
| PostgREST | Компактный синтаксис в URL | Только Postgres; можно добавить вторым входом поверх того же `QueryCriteria` |

## Этапы

1. Валидатор и транслятор с контрактными тестами на операторы; `data.schema`; `data.query` только
   чтение, вместе с `total`. Тесты: `total` по модели с правами на записи и по модели по точкам равен
   числу записей в списке, который человек видит; «пользователь × модель × операция» — в схеме ровно то, что проходит запрос; чужое
   поле не видно ни в схеме, ни в ответе и не принимается в `where` / `sort` / `select` / `populate`.
2. `data.mutate` и `protectField`; тест «`order.state` нельзя записать через `data.mutate`».
3. Автоэкраны в клиенте: приложение «Данные» для всех, у кого есть чтение моделей, построитель
   критериев, формы по схеме, число записей в заголовке списка.
