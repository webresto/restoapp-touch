## Что теперь стоит

- **adminizer 5.2.0-build.33** — последний опубликованный билд (`npm view adminizer dist-tags`:
  `alpha` = 5.2.0-build.33; `latest` 4.6.0 и `next` 4.7.0-build.224 — старые ветки).
  Закреплён **в корне restoapp-dev**, для оба пакетных менеджера:
  - `package.json` — `overrides: { "adminizer": "5.2.0-build.33" }`; adminizer приходит транзитивно
    (`sails-adminpanel` → `adminizer: alpha`), своей строки в `dependencies` у него нет, поэтому
    закрепление — через `overrides`. Было 5.1.0-build.27.
  - **Лок сабмодуля `local_modules/core` оставлен как был** (`alpha` → 5.2.0-build.32) — решение
    владельца. В образе `local_modules` удаляется и работает корневая установка, так что на прод лок
    core не влияет; закреплять точный билд там — отдельной веткой в `webresto/core`. Срез 0 плана
    просил «один билд в обоих локфайлах», но практического смысла в этом нет, а сдвигать gitlink
    сабмодуля на локальный коммит — нет.
  - `yarn.lock` — тот же билд: образ собирается через `yarn --immutable workspaces focus
    --production` (`Dockerfile:41`), поэтому в `package.json` рядом с `overrides` стоит и
    `resolutions`, а в `yarn.lock` запись ключом `adminizer@5.2.0-build.33, adminizer@alpha` —
    чтобы запрос `alpha` от `sails-adminpanel` решался в тот же точный билд.
  - `npm install --ignore-scripts` поменял ровно один пакет. `.ci/patchset` adminizer не патчит —
    проверено, конфликтов нет.
- **Осторожно с npm 11:** любой `npm install` в этом репозитории переписывает и `yarn.lock`, добавляя
  47/29 строк шума про платформу (`@esbuild/win32-x64` → `@esbuild/darwin-x64` и т.п.). В текущем
  диффе этого шума нет: `yarn.lock` возвращён из индекса и правлен только по записи adminizer. Если
  снова запустить `npm install` — проверить `git diff yarn.lock`.
- **Чего проверить не вышло:** сборка образа. Ни Docker, ни yarn на этой машине нет, поэтому
  `yarn --immutable` с этим локфайлом не прогонялся. Локфайл в формате yarn v1, а Dockerfile ставит
  berry (`yarn set version berry`) — если `--immutable` на нём упадёт, у Dockerfile есть ветка с
  переустановкой без `--immutable`, но лучше прогнать сборку перед релизом.

## Стенд: `tools/real-server/`

`serve.ts` — настоящий сервер целиком, а не хук на фальшивых `deps` (это `tools/fake-server/`):
поднятый Sails, веб-админка adminizer 5.2, системный хук `app-mobile-api`, настоящие модели core
(`Dish`, `DishPlace`, `Place`, `Order`, `OrderDish`), `AccessRightsHelper` и контекстные права.
База — sails-disk во временном каталоге, свежая на каждый запуск.

```sh
cd ../restoapp-dev && npx tsx ../restoapp-mobile-admin/tools/real-server/serve.ts 1341
```

Фикстуры (те же логины и id, что у `fake-server`, чтобы один и тот же тест клиента ходил на любой):

| | |
|---|---|
| Точки | `p1` «Ленина, 5» (кухня + выдача), `p2` «Мира, 3» (кухня), `p3` «Выдача» (только выдача) |
| Блюда | `d1` Борщ 300 B1 (Супы), `d2` Плов 450 P1 (Горячее), `d3` Морс 120 M1 (Напитки) |
| Люди | `admin` (администратор), `stock` (Stock Manager на p1 и p2), `operator` (Operator), `nopoints` (токен без галочек точек), `outsider` (без доступа в админку) — пароль у всех `secret-password` |

Управление для тестов — `POST /__fake/…`: `stock-points`, `password`, `reset-password`,
`clear-attempts`, `clear-stock`, `reset-catalog`, `bulk-dishes`, `drop-bulk-dishes`, `order`, `move`;
`GET /__fake/orders`, `/__fake/web-stock`, `/__fake/dish-place`. Полный список — в шапке `serve.ts`.

Две правки, без которых стенд не поднимался:
- `TZ` обязателен: без него `Order.checkDate` бросает `code 19` «Server timezone is not configured,
  ordering is disabled», и заказ не оформить вообще.
- Группы `Stock Manager` и `Operator` создают сами хук и core, поэтому фикстуры делают upsert по
  имени, а не `create` (иначе `uniqueViolated`).
- `Place.address` — строка, `null` не проходит валидацию (у `p3` адрес `""`).

В `tests/support/liftWithAdminpanel.ts` (restoapp-dev) добавлен `fixtures: false` и отдан `dir`
датастора — стенд поднимает тот же Sails, но со своими записями.

### 2. Мобильный API целиком: `tools/real-server/walk.ts` — всё зелёное

```sh
cd ../restoapp-dev && npx tsx ../restoapp-mobile-admin/tools/real-server/walk.ts
```

Печатает каждый шаг. Разделы:

- **`server.about` без токена** — отвечает `{name, version}`.
- **Кто что получает.** `admin` — «Блюда» на обеих кухнях; `stock` — на своих p1 и p2; `operator` —
  приложений нет; `nopoints` — «Блюда» есть, точек ноль; `outsider` — `forbidden`, войти не может.
  У каждого своя ревизия.
- **Вход.** Неверный пароль и несуществующий логин — один и тот же `invalid_credentials`. Решённая
  капча второй раз — `captcha_invalid`. Лимит входов срабатывает на 11-й попытке (10/мин на IP).
- **«Блюда» по точкам.** `setBalance` 7 на Борщ при p1 → ответ несёт обновлённую запись с
  `groupTitle` «Супы»; список p1 показывает Борщ, список p2 — пусто; точки не смешиваются.
- **Веб-склад читает то же число.** `getStockProducts('p1', d1)` → `balance` 7, на p2 → −1; строка
  `DishPlace` — `localBalance` 7. То есть приложение и веб-админка пишут в одно место.
- **Каталог, поиск, страницы.** 3 блюда с `total`; поиск по коду `P1` → Плов; лишний параметр
  (`limit`) отвергается — размер страницы серверный; чужой курсор отвергается. На каталоге из 63
  блюд: первая страница 50 с курсором, вторая 13 и последняя, вместе — 63 различных id, ничего не
  потеряно и не удвоено; счётчики на чипсах — 63 и 1.
- **Карточка, «В продаже», спецзначения.** Карточка несёт два действия, которые разрешают права.
  «В продаже» выключили — ручная 7 осталась, действующий остаток стал 0 (стоп); включили — 7 снова
  в силе. Стоп 0, «Безлимит» −1, −2 схема не пускает.
- **Что сервер отвергает.** Точка вне группы — `place_forbidden`; без точки — отказ; строка вместо
  числа — `invalid`; неизвестное блюдо — отказ; `operator`, вызывающий метод «Блюд», — `forbidden`;
  без токена — 401; неизвестный метод — отказ.
- **Права меняются под работающим устройством.** Сняли p2 у группы — на следующем запросе
  `place_forbidden` и другая ревизия в `X-Mobile-Revision`, p1 работает.
- **Смена пароля** — старый токен 401.
- **Блюдо, созданное в веб-админке**, видно в «Блюдах» без перезапуска: с ценой из панели, и
  приложение ставит ему остаток, который читает веб-склад.

### 2a. «Заказы» среза 2 — в том же прогоне `walk.ts` (2026-11-03, вечер)

Срез 2 сделан (core: `orders-by-place`, хук: `apps/orders.ts`), и прогон заказов теперь настоящий —
не «нечем пройти», как было днём. Разделы `walk.ts`:

- **Кто что получает** — `operator` теперь: приложения `["orders"]`, точки `["p1", "no-kitchen"]`
  («Без кухни» — опция контекстного токена `order-kanban`, не `Place`). «Блюд» у него по-прежнему нет.
- **«Заказы» на p1.** Заказ p1 в списке, заказ p2 — нет; на чипсах счётчики точки; карточка несёт
  состав («2 × Борщ»), клиента из чекаута и единственное действие `orders.setState` с переходами
  `["COOKING","ON_THE_WAY","DONE","REJECT"]` — ровно то, что разрешает роль оператора в `OrderStateFlow`.
- **Опрос с `since`.** Сразу после чтения карточки `since = updatedAt + 1` даёт пустую страницу.
  Веб-доска переводит заказ в COOKING (тот же `transitionOrder`) — и следующий опрос с тем же `since`
  отдаёт только эту строку, уже в COOKING. То есть телефон узнаёт о чужом переходе без SSE.
- **Проход с телефона** — `ON_THE_WAY`, `DONE`; база сервера согласна (`state: DONE`), заказ ушёл в
  «Завершённые», и у завершённого `_actions` пуст — только чтение.
- **Чужая точка.** p2 — `place_forbidden`; её заказ по прямому id — `not_found`; перевести — тоже
  `not_found` (не 403: по id сервер говорит не больше, чем в списке).
- **«Без кухни» и «Назначить кухню».** Доставка без кухни ждёт на своей точке, в строке есть
  `orders.assignKitchen` с enum кухонь **этого** человека (`["p1"]`); назначили — заказ ушёл из
  «Без кухни» и появился среди заказов p1; «Отклонить» с телефона работает.

## Чего нет

1. **Остановок заказа (`OrderStop`, задача C2) нет** — поэтому заказы точки выбираются
   ограниченным чтением активных (и завершённых за 7 дней) заказов всей сети с фильтром по точке
   в памяти (`lib/order/orders-of-place.ts`, предел 2000). На загруженной сети этого мало: нужна
   C2 с индексом `(place, orderState)`. Всё остальное из среза 2 сделано и пройдено на настоящем
   сервере (раздел 2a); доска админки тоже переведена на точки (C1) и на одну функцию перехода (C5),
   «Назначить кухню» (C6) есть и в доске, и в телефоне.
2. **Postgres и Docker** — на этой машине нет ни того, ни другого. Стенд на sails-disk, миграции хука
   (`migrations/20261103160000-mobile-api-init.js`) не прогонялись, образ не собирался.
3. **Кластер pm2** — проверяли один процесс. Капча в кластере по-прежнему сломана (`POWCaptcha`
   adminizer держит задачи в памяти процесса); изменение в adminizer upstream не начато.
4. **Веб-капча включена** (`ENABLE_ADMIN_CAPTCHA=true`) и на стенде работает, но со сложностью 20 мс.

## Что нашлось попутно

1. **Поиск по каталогу чувствителен к регистру.** `filter: all` уходит в Waterline `contains`
   (`adapters/stock.ts: listCatalog`), а это `LIKE` и на sails-disk, и на Postgres: «мор» не находит
   «Морс», «Мор» находит. При этом `filter: limited` и `filter: stop` фильтруются в памяти функцией
   `matches()`, которая приводит к нижнему регистру. Один и тот же запрос ведёт себя по-разному в
   зависимости от чипа, и на телефоне (где пишут строчными) каталог почти не ищется. Веб-поиск core
   устроен так же, так что чинить — в `listCatalog` и в веб-функции заодно.
2. **`crypto-puzzle` на Node падает** с `DOMException: Cipher job failed` на задаче, у которой первый
   байт ключа — ноль (примерно 1 из 256). Ловили на первой же попытке. Kotlin-решатель клиента такие
   задачи открывает, а JS-решатель веб-входа — нет: раз в 256 входов человек в браузере получит
   ошибку капчи. Это та же открытая задача, что записана в плане; теперь она подтверждена на
   настоящем сервере. Инструменты обходят её, запрашивая другую задачу, и считают такие отказы.
3. **Переключатель «В продаже» отдаёт состояние как `Selected`, а не `ToggleableState`** —
   `SwitchControl` в `render/Components.kt` ставит `semantics { selected = checked }` при
   `Role.Switch`. Тесты вынуждены писать `assertIsSelected()` вместо `assertIsOn()`, и программы
   чтения с экрана, скорее всего, прочитают его как «выбрано», а не «включено».
4. **Ассоциацию `parentGroup` панель так не принимает:** `POST /admin/model/dish/add` с
   `parentGroup: "g-hot"` создаёт блюдо, но без группы, и в «Блюдах» оно показывается без заголовка
   группы (`groupTitle` пустой). Формат, которого ждёт форма панели для связи, — не плоский id;
   разбираться, если захочется заводить блюда скриптом через панель.
5. **Стенд накапливает состояние между прогонами** (пароли, остатки, блюда из панели). И `walk.ts`, и
   `RealServerWalkTest` начинаются со сброса (`reset-password`, `reset-catalog`, `clear-stock`,
   `clear-attempts`, `stock-points`) — иначе второй прогон падает на том, что первый поменял.
