## Идея

Приложение сервера — один JS-файл. Сервер отдаёт его вместе с декларацией, клиент выполняет его в
QuickJS и рисует экран, который JS вернул **данными**, компонентами `superizer:ui`. Для Superizer
это ещё одна реализация `SuperizerApp` / `AppInstance`; контракт не меняется.

Это Tier 3 из разбора Unitool («логика в песочнице + декларативный UI, который рисует хост»), но
движок — QuickJS, а не wasm (wasm там был слабым звеном, QuickJS проверен прототипом). Главное
предупреждение того разбора в силе: **набор компонентов — это продукт, а не функция**.

**Без JSX и без Preact.** `view(state)` возвращает весь экран, старое и новое дерево сравнивает
Compose по ключам. JSX — только синтаксис: при желании компилируется в те же вызовы `ui.*`.

**Разделение труда: JS решает, Kotlin делает.** В JS — логика и маленькое состояние экрана (фильтр,
открытая запись, шаг мастера). В Kotlin — всё большое и всё частое: данные списков, ввод текста,
прокрутка, сеть, опрос, форматирование, анимации, переходы. JS не держит массив из 10 000 заказов и
не получает событие на каждую букву или каждый пиксель прокрутки. Так экран остаётся маленьким
деревом (сотня-другая узлов), и полная перерисовка стоит меньше миллисекунды.

## Что уже проверено (прототип `quick/`, этот Mac)

- quickjs-kt 1.0.15: нативная библиотека для Intel-Mac, macOS 11.7+; JDK 17; Kotlin 2.4.10 и Compose
  1.11.1, как в проекте. Android и iOS библиотека умеет — не проверялось.
- Нажатие в Compose → JS → новый экран; Promise в JS ↔ suspend в Kotlin; таймеры ведёт Kotlin;
  бесконечный цикл прерывается через ~250 мс, рантайм работает дальше.
- Весь экран данными: список из 500 строк — 59 КБ JSON, ~6 мс на обновление; круг нажатия < 1 мс;
  запуск рантайма 10–20 мс. С коллекциями на хосте (раздел 5) строки в JS вообще не попадают.
- Сторы: Google Play исключает интерпретируемый JS из запрета на загрузку кода; Apple
  (лицензионное соглашение, §3.3.1(B)) разрешает такой код, если он не меняет назначение
  приложения. Веб-хост: тот же JS выполняет браузер, QuickJS не нужен.

## 1. Сколько менять в Superizer

**Переписывать — ничего.** Контракт (`SuperizerApp`, `AppInstance`, `AppRuntime`, сервисы) остаётся
как есть, Unitool не затрагивается. Всё — дописать:

| Модуль | Что | Объём (прикидка) |
|---|---|---|
| `core` | ничего: манифест уже сериализуемый, `networkHosts` уже задуман как список разрешённых адресов для моста, поздняя регистрация приложений уже есть | 0 |
| `ui` | недостающие компоненты: строка списка, бейдж, чипы, степпер, поиск, пусто / загрузка / ошибка, подтверждение, нижняя шторка, вкладки | ~1 тыс. строк |
| `script` — новый модуль | рантайм QuickJS, протокол, рендер дерева, маршруты, коллекции, выражения, действия, сеть, ошибки, кеш байткода; JS-прелюдия `ui` / `act` / `$`; `ui.schema.json` | ~3–4 тыс. строк Kotlin + ~600 JS |
| `testing` | `ScriptTestHost` — гонять скрипт в тестах без окна | ~300 строк |
| `host` | доступ скриптов к необязательным сервисам хоста (`ServiceKey`) | до 50 строк |

Итого около 5 тыс. строк к нынешним ~21 тыс. Компоненты из строки `ui` нужны и универсальному
рендеру плана v2, то есть это общая работа. Сейчас `Chip` и строка списка уже написаны дважды — в
`apps/stock` и `apps/orders`, — им место в `superizer:ui` в любом случае.

## 2. Приложение — один файл

```js
// dishes.js — лежит в модуле на сервере, сборки нет
app({
  stores: { dishes: { key: "id", persist: true } },          // данные живут в Kotlin, не в JS

  routes: {
    list: {
      async enter(ctx, params, saved) {
        const filter = saved?.filter ?? "limited"
        await ctx.server.call("dishes.list", { filter }, { into: "dishes", replace: true })
        return { filter, q: saved?.q ?? "" }
      },
      view: (s, ctx) => ui.column([
        ui.search({ id: "q", debounce: 200, onChange: q => ({ q }) }),
        ui.chips({
          value: s.filter,
          options: { limited: ctx.t("limited"), stop: ctx.t("stop"), all: ctx.t("all") },
          onChange: async filter => {
            await ctx.server.call("dishes.list", { filter }, { into: "dishes", replace: true })
            return { filter }
          },
        }),
        ui.list({
          source: "dishes", where: { name: { contains: s.q } }, groupBy: "parentGroup",
          row: ui.row({                                        // шаблон: Kotlin рисует видимые строки сам
            title: $.name, subtitle: $.parentGroup,
            value: $.balance.lt(0).then("∞", $.balance),
            tone: $.balance.eq(0).then("danger"),
            onPress: act.push("dish", { id: $.id }),
            trailing: ctx.can("dishes.setBalance") && ui.stepper({
              value: $.balance, min: -1,
              onChange: act.call("dishes.setBalance", { id: $.id, balance: $event },
                                 { into: "dishes", optimistic: { balance: $event } }),
            }),
          }),
          empty: ui.empty(ctx.t("empty")),
        }),
      ]),
      snapshot: s => ({ filter: s.filter, q: s.q }),
    },

    dish: {
      path: "dish/:id",
      async enter(ctx, { id }) {
        const { item } = await ctx.server.call("dishes.get", { id }, { into: "dishes" })
        return { id, name: item.name }
      },
      title: s => s.name,
      view: (s, ctx) => ui.record({ source: "dishes", id: s.id, body: ui.section([ /* … */ ]) }),
    },
  },

  strings: { ru: { limited: "Учёт", stop: "Стоп", all: "Все", empty: "Ничего не нашлось" }, en: { /* … */ } },
})
```

Правила:

- **Состояние экрана — JSON** (без функций, объектов-дат и циклов). Большие данные — в коллекциях.
- **Обработчик-функция** возвращает ничего, частичное состояние (сливается с текущим), функцию
  `state => частичное состояние` или Promise одного из них. Хост применяет результат к состоянию **на
  момент ответа**, а не к тому, что было при отрисовке, — иначе медленный запрос затрёт то, что
  человек успел поменять.
- **`ctx`:** `server` (раздел 6), `stores.<имя>`, `can(method)` — есть ли метод у этого человека,
  `place`, `nav` (раздел 3), `ui` — команды элементам (раздел 6), `storage`, `t(key)`, `locale`,
  `after` / `every`, `log`, `services.<имя>`. Больше ничего: ни `fetch`, ни файлов, ни токена.
- Обязательны только `routes` (хотя бы один) и `view` у маршрута. Первый маршрут — стартовый.

## 3. Маршруты внутри приложения

Стек ведёт **хост**, не JS.

- **Маршрут** — имя, параметры (JSON) и своё состояние. Хуки: `enter(ctx, params, saved)` →
  состояние; `view`; `title` / `subtitle`; `snapshot`; `canLeave(state)` — для несохранённой формы;
  `leave`.
- **Переходы.** `ctx.nav.push(route, params)`, `replace`, `back()`, `reset(route)`; в разметке без JS
  — `act.push(...)`, `act.back()`. Виды маршрута: `screen` (по умолчанию), `sheet` (шторка снизу),
  `dialog`. Вкладки — компонент `ui.tabs` внутри маршрута; выбранная вкладка живёт в Kotlin.
- **Назад.** Стек длиннее одного → `AppChrome.canGoBack = true`, заголовок — `title` верхнего
  маршрута; «назад» снимает маршрут сам (`SystemBackHandler`), JS спрашивается только при
  `canLeave`. Уход из приложения — `onCloseRequested` Superizer, тот же `canLeave`.
- **Снимок.** `saveState()` = стек `[(route, params, snapshot)]`; `restore` поднимает его, и
  приложение открывается там же, где было (правило Superizer). `enter` верхнего маршрута вызывается
  сразу, нижних — когда до них дойдут «назад».
- **Глубокие ссылки и пуши.** `path: "dish/:id"` → `manifest.deepLinks` и `setup(ctx).deepLink(...)`:
  ссылка или пуш открывают приложение сразу на маршруте.
- **Другие приложения.** `ctx.nav.openApp("orders", { route: "order", params: { id } })` →
  `NavigationService.openApp(id, config)` Superizer; маршрут и параметры едут в `ScriptConfig`.
- Анимации переходов — хост.

## 4. Разметка: формат и откуда приходит

**Формат.** Дерево узлов; одно и то же, откуда бы оно ни пришло:

```jsonc
{ "t": "list", "k": "dishes",                                   // тип, ключ
  "p": { "source": "dishes", "where": { "name": { "contains": "бор" } }, "groupBy": "parentGroup" },
  "item": { "t": "row",                                         // шаблон строки — данные из коллекции
    "p": { "title": { "$": "name" },
           "tone": { "if": { "eq": [{ "$": "balance" }, 0] }, "then": "danger" } },
    "on": { "press": { "do": "push", "route": "dish", "params": { "id": { "$": "id" } } } } },
  "c": [] }                                                     // дети
```

- `on` — номер обработчика в JS (для `view` скрипта) или **действие** (`do`), которое хост выполнит
  сам (раздел 6).
- **Выражения** — маленький язык для шаблонов, без циклов и функций: `$` (поле записи), `$event`
  (значение события), `eq ne lt lte gt gte and or not in contains`, `if/then/else`, `concat`, `plus`,
  `minus`, `fmt` (money, datetime, relative, phone, plural). Kotlin считает их для каждой видимой
  строки; JS для этого не нужен. В JS их пишут через `$.balance.eq(0).then("danger")`.

**Откуда приходит** — три источника, один рендер:

1. **Скрипт на устройстве** (основной): `view` выполняется в QuickJS на каждое изменение.
2. **Готовая разметка в скрипте**: маршрут с `markup` вместо `view` и только действиями `do` — JS
   на этом экране вообще не выполняется.
3. **Разметка с сервера на запрос**: метод отдаёт `{ ui: дерево }`, маршрут показывает его через
   `ui.remote("dishes.screen", params)`, действия идут на сервер, он отдаёт новое дерево. Для редких
   экранов — настроек, справочников. Каждое нажатие — запрос, поэтому не для ввода.

Нужны все три (Q6). Формат допускает (2) и (3) с первого дня; первым делается (1), а (2) и (3) — с
первым экраном, которому не нужна логика на устройстве (этап 5).

## 5. Данные на хосте — коллекции

Большие массивы живут в Kotlin. JS держит только имя коллекции.

- **Объявление:** `stores: { dishes: { key: "id", persist: true } }`. Коллекция своя у экземпляра
  приложения; с `persist` — сохраняется в хранилище приложения на этом сервере, и список открывается
  мгновенно и без сети.
- **Заполнение мимо JS:** `ctx.server.call(m, p, { into: "dishes", replace })` — хост сам разбирает
  ответ и кладёт `items` (или `item`) в коллекцию. В JS возвращается всё, кроме массива `items`:
  `nextCursor`, `counts`, одна запись.
- **Показ:** `ui.list({ source, where, sort, groupBy, row })` — Kotlin фильтрует, сортирует и рисует
  только видимые строки (`LazyColumn`) по шаблону `row`. `where` / `sort` — подмножество
  `QueryCriteria` из `data-query-layer.plan.md`, поэтому тот же фильтр можно отправить на сервер, если
  данных больше, чем загружено (`list` с `remote: "dishes.list"` подгружает страницы по
  `nextCursor` сам).
- **Чтение из JS — понемногу:** `await ctx.stores.dishes.get(id)`, `find(where, { limit })`,
  `count(where)`. Целиком коллекцию в JS не отдаём.
- **Изменение:** ответ мутации с `into` обновляет запись сам; `optimistic` — сразу, с откатом и
  сообщением, если сервер отказал. Из JS — `patch(id, частичная запись)`, `remove`, `clear`.
- **Лимиты:** до 50 тыс. записей и 20 МБ на коллекцию (уточнить замером); больше — только `remote`.

## 6. Что делает хост вместо JS

**Элементы.** Состояние элементов живёт в Kotlin: текст и курсор полей, фокус, прокрутка, раскрытые
секции, выбранная вкладка, открытая шторка, «потянуть, чтобы обновить».
- JS получает только значимые события: `onChange` с `debounce`, `onSubmit`, `onRefresh`.
- Команды по `id` элемента, без перерисовки: `ctx.ui.focus("q")`, `scrollTo("list", key)`,
  `clear("q")`, `toast(text)`, `await ctx.ui.confirm(text)`.
- Само собой: кнопка, чей обработчик вернул Promise, крутит индикатор и не нажимается повторно;
  «потянуть» ждёт Promise из `onRefresh`.
- **Формы по схеме:** `ui.form({ method: "dishes.setBalance", values })` — поля, проверка и
  ошибки по JSON Schema метода из декларации; отправка — `call` с `into`. Это та же форма, что у
  универсального рендера плана v2.

**Действия без JS** (`act.*` в JS, `do` в разметке): `call(method, params, {into, optimistic,
confirm, then})`, `push`, `back`, `openApp`, `url`, `copy`, `toast`, `refresh(store)`, `seq(...)`;
`act.js(handler, $.id)` — когда всё-таки нужен JS, с ключом строки. В шаблонах строк списков
работают только действия: строки рисует Kotlin, замыканий JS у них нет.

**Сеть.** Всё через хост:
- `ctx.server.call` — токен, точка, таймаут, повтор при `retryable`, один запрос вместо нескольких
  одинаковых одновременных, кеш запросов (`cache: 15`, в секундах), ревизия и ошибки 401 / 403 / 429
  — как в разделе 4 плана v2.
- `ctx.server.watch(method, params, { every: 15000, into, since })` — опрос ведёт хост, он же
  останавливает его в фоне и при закрытии приложения и сливает изменения по `since` (заказы в плане
  v2 так и обновляются). JS узнаёт об изменениях, только если подписался.
- `ctx.http` — только к адресам из `manifest.networkHosts` (Superizer так это поле и задумал).
- Без сети: коллекции с `persist` показывают последнее, изменения — ошибка «Нет связи» (очередь
  изменений офлайн — не в первой версии).

**Остальное.**
- Форматирование: деньги, даты, «5 минут назад», телефоны, множественное число — по
  `server.currency` / `server.timezone` и языку.
- Строки: `strings` скрипта + `ctx.t`; язык выбирает `LocaleService`.
- Сервисы хоста по `ServiceKey` (сканер QR, принтер чеков, буфер обмена, «поделиться», вибро) —
  `ctx.services.<имя>`, если объявлены в `requires`.
- Тяжёлые вычисления — методом на сервере, а не в JS.

**Скорость самого JS.**
- Байткод: скрипт компилируется один раз и кешируется по (sha256, версия QuickJS); следующие запуски
  без разбора текста.
- Несколько изменений состояния за одно событие → одна перерисовка.
- `ui.memo(key, deps, fn)` — неизменившееся поддерево не собирается заново. Нужно, только если экран
  станет большим, — с коллекциями вряд ли.
- Формат — JSON; двоичный не нужен (замер в `quick/`).

## 7. Компоненты — одна система для клиента и сервера

**Источник правды — `ui.schema.json`** в модуле `superizer:script`: каталог компонентов (имя, с какой
версии, свойства и их типы, где допустимы выражения, события), действия и операторы выражений.
Версия схемы — `uiVersion`.

Из неё получаются:
- **npm-пакет `@superizer/ui`**: `ui.*`, `act.*`, `$` и типы TypeScript, ~500 строк. Живёт в
  репозитории Superizer и публикуется в npm с той же версией, что Superizer (Q5). Тот же код встроен
  в хост как прелюдия, поэтому скрипт пакет не включает и версии не расходятся.
- **Kotlin:** контрактный тест — рендер знает каждый компонент схемы; скриншот-тесты на образцах;
  экран-галерея всех компонентов в сервисном меню Superizer (отладочная сборка).

**Что это даёт на бэке (restoapp-dev):**
1. Скрипты пишутся с типами и автодополнением: `import { ui, act, $ } from '@superizer/ui'`.
   Типы строк — из схем методов, поэтому `$.balance` подсказывается, а `$.balanse` — ошибка.
2. Скрипт тестируется в Node (vitest) без устройства: `view` с поддельным `ctx` → снимок дерева,
   нажатия → новое состояние. В CI restoapp-dev.
3. При старте сервера каждый зарегистрированный скрипт прогоняется на образцах и проверяется по
   схеме — ошибка видна при выкатке, а не на телефоне. Так же, как `declaration.schema.json` в
   плане v2.
4. Разметку можно строить на сервере теми же функциями — источники (2) и (3) раздела 4. Туда же со
   временем может переехать универсальный рендер плана v2: сервер превращает подсказки `ui` методов
   в дерево, и клиенту остаётся один рендер (Q3).

**Версии.** Клиент сообщает `uiVersion` в запросе `describe`. Скрипт объявляет, какая версия ему
нужна; сервер не отдаёт скрипт клиенту, который его не нарисует, — показывается плитка «Нужна новая
версия приложения». Незнакомый компонент в рантайме — заглушка на его месте, не падение.

**Ввод текста живёт в Kotlin.** JS получает `onChange`, но не возвращает значение в поле на каждую
букву — иначе прыгает курсор (известная беда React Native). Сбросить поле — `ctx.ui.clear(id)`.

**Состав `ui` v1.** Раскладка: `column`, `row`, `section`, `divider`, `tabs`. Текст: `text`
(стиль и тон), `badge`, `money`, `datetime`. Действия: `button` (вариант, подтверждение),
`iconButton`. Ввод: `textField`, `search`, `toggle`, `stepper`, `chips`, `choice`, `form`. Данные:
`list` + `row`, `record`. Состояния: `loading`, `empty`, `error`. Наложения: `sheet`, `confirm`,
`toast`. Цвета и размеры из JS не задаются — только тоны и стили Superizer (цвет в Superizer —
только для состояния).

## 8. Хост — модуль `superizer:script`

- **Где.** В Superizer, отдельным модулем (D4 RestoApp: всё через Superizer). Unitool не тянет
  QuickJS, пока не подключит модуль. Superizer не знает про RestoApp: `ctx.server` — **именованный
  сервис скрипта** (`ScriptService`: имя + `suspend call(method, json) → json` + описание методов
  для `can`). RestoApp регистрирует `server` поверх `RestoServer` из плана v2; Unitool сможет дать
  свои.
- **`ScriptApp(manifest, script, services)`** : `SuperizerApp<ScriptConfig>`; `manifest` — из
  декларации (название, иконка, категория, глубокие ссылки), поэтому плитка есть до загрузки скрипта.
- **`ScriptInstance`** : `AppInstance`:

  | Superizer | Скрипт |
  |---|---|
  | `onLaunch()` | загрузка (из кеша байткода), рантайм, коллекции с `persist` |
  | `restore(state)` | стек маршрутов со снимками |
  | первый кадр `Content()` | `enter` верхнего маршрута; до ответа — `loading` |
  | `Content()` | `view` верхнего маршрута → дерево → компоненты |
  | `chrome` | `title` / `subtitle` маршрута, `canGoBack` по стеку |
  | `SystemBackHandler` | снять маршрут; `canLeave`, если есть |
  | `saveState()` | стек + последние `snapshot` — считаются после каждого изменения, поэтому без вызова JS |
  | `onBackground` / `onForeground` | `watch` и `every` останавливаются / продолжаются |
  | `onCloseRequested()` | `canLeave` маршрутов стека |
  | `dispose()` | рантайм, таймеры, запросы — отменены |

- **Рантайм.** Один QuickJS на открытое приложение (в Superizer открыт не больше одного экземпляра
  приложения), свой поток; все входы в JS — по одному; цикл событий ведёт Kotlin, как в прототипе.
  Лимиты: память 32 МБ, стек 512 КБ, 250 мс на вызов.
- **Ошибки.** Исключение в `view` или обработчике, превышение лимита, битая разметка → экран ошибки
  приложения («Что-то пошло не так» + «Перезапустить»), в лог — версия скрипта, маршрут и стек. Хост
  не падает. Номера строк в стеке настоящие: сборки нет.

## 9. Доставка

- **Сервер.** `mobileApi.registerApp({ …, script: 'mobile/dishes.js' })` — файл в модуле. Хук читает
  его при старте, проверяет (раздел 7, пункт 3), считает sha256 и отдаёт
  `GET /api/mobile/script/:app/:sha256` с тем же токеном и той же проверкой доступа, что у
  приложения (нет доступа — 404). Ответ по хешу неизменяем — кешируется навсегда.
- **Декларация.** У приложения — `script: { sha256, size, uiVersion }`. Методы со схемами остаются:
  на них держатся `ctx.can`, типы строк и права. Подсказки `ui` у методов скриптового приложения не
  нужны.
- **Ревизия.** В хеш ревизии добавляются sha256 скриптов: новый скрипт = новая ревизия → клиент
  перечитывает `describe` (это уже есть в плане v2) → скачивает → пересобирает Superizer сервера →
  открытое приложение восстанавливается из снимка.
- **Клиент.** Качает через `RestoServer`, сверяет sha256 и размер, кладёт в
  `~/.restoapp/servers/<id>/scripts/<app>/<sha256>.js` (рядом — байткод). Хранит текущую версию и
  предыдущую, которая запускалась без ошибок; остальные удаляет. Без сети — из кеша.
- **Откат.** Новая версия упала в `enter` или первом `view` → запускается предыдущая, в лог —
  причина. Человек видит приложение, а не ошибку.
- **Подпись — не сейчас.** Скрипт приходит с того же сервера, по HTTPS, с тем же токеном; взломанный
  сервер и так управляет данными. Подпись (Ed25519, ключ автора модуля) — если скрипты начнут
  приходить со стороны (Q2).
- **Демо-сервер** отдаёт скрипты из ресурсов клиента тем же путём.

## 10. Права и безопасность

- JS видит только `ctx`. `server.call` и действия `call` идут тем же `POST /api/mobile/call/:method`
  с той же проверкой прав: скрипт не может больше, чем человек. Чужой метод хост не пропустит — как
  в плане v2.
- Лимиты памяти и времени защищают интерфейс от зависаний, но **QuickJS — не граница
  безопасности**. Это нормально, пока код приходит с собственного сервера (Q2).

## 11. Что это меняет в других планах

- **`server-apps-and-rights.plan.md`.** Серверная часть не меняется: реестр, права, вход с PoW,
  точки, `call`. Клиент первого релиза — универсальный рендер. Два задела сделаны в версии 2.5 сразу,
  потому что потом они дороже: поле `script` зарезервировано, и клиент без скриптов показывает такое
  приложение плиткой «Нужна новая версия» (раздел 5 плана v2); рендер собирается из небольших
  компонентов с JSON-совместимыми параметрами (раздел 4 плана v2) — это и есть будущий `ui` v1.
- **`data-query-layer.plan.md`.** `where` / `sort` коллекций — подмножество его `QueryCriteria`.
  Автоэкраны можно сделать скриптом или разметкой с сервера, а не кодом клиента (Q3).

## 12. Каталоги-деревья: навигация и товары (D12)

Владелец (2026-11-04): «надо сделать модуль редактирования навигации как модуль на js». Это ответ на
разбор «что ещё вынести из админки», где навигация стояла в «не нести»: нести, но не кодом клиента.

**Почему не декларацией и не нативно.** Дерево с вложенностью, порядком и переносом ветки
декларацией v1 (`list` / `detail` / `action`) не описывается, а зашивать такой редактор в клиент
незачем — его открывают раз в месяц. Главное же: **модуль админки приносит свой мобильный экран
сам**. Навигацию даёт `sails-adminpanel/apps/navigation` (`NavigationApp.mjs`, `NavigationCatalog.mjs`),
вместе с ней приходит и её экран — ровно то, ради чего затеян D9.

**Один редактор на два каталога.** Навигация и «Товары» — один механизм adminizer: `ctx.catalog` и
`AbstractCatalog` (`getChilds`, `find`, `deleteItem`, `getAddTemplate` / `getEditTemplate`,
`getActions` / `handleAction`, `getitemTypes`, `setId` — раздел каталога). Так устроен и
`local_modules/core/lib/adminpanel/ProductCatalog`. Один экран дерева закрывает оба, а каталог
товаров — самое дорогое из того, что ещё не вынесено.

**Чего сегодня нет: самой навигации.** В RestoApp она выключена пустым конфигом —
`config/adminpanel.js:112`, `navigation: { items: [], sections: [] }`; комментарий там объясняет
зачем: без блока `NavigationApp.setup()` падает на `config.items.map`, и `/admin` молча уходит в SPA.
Править пока нечего — сначала решается, что такое навигация на этом сервере (Q8).

**На сервере** (хук `app-mobile-api`, методы как у остальных приложений, права — токены
`catalog-navigation` и `catalog-products`, `scope: "server"`): разделы каталога (`getIdList`), типы
элементов (`getitemTypes`), дети узла (`getChilds`), поиск, добавление, правка, удаление
(`deleteItem`), перенос (запись `parentId` и `sortOrder`), действия каталога (`handleAction`).
Хук зовёт объект каталога напрямую, как зовёт функции core, — веб-роуты `/catalog/:slug` отдают
Inertia-страницу и для нас бесполезны.

**Формы с веба не переезжают.** `getAddTemplate` / `getEditTemplate` отдают React-шаблоны и ссылки
на формы моделей админки (`/model/<resource>/add`). Группа и ссылка (`navigation.group`,
`navigation.link`) — это пара полей, их схема пишется руками, как у остальных методов хука. А
`model-link` и товар — это форма модели, и она ждёт `data-query-layer.plan.md`: то есть навигация
едет первой, товары — за слоем данных.

**В клиенте** нужен один новый компонент — дерево: уровни, раскрытие, порядок. Раскрытие и прокрутка
живут в Kotlin (раздел 6), поэтому на каждое раскрытие JS не нужен. Таскания на телефоне не делаем:
перенос — действием «Переместить в…» (выбор родителя и места), Q9.

**Скрипт или разметка с сервера.** Редактору не нужна логика на устройстве: состояние дерева ведёт
хост, ввод — формы по JSON Schema, каждое нажатие и так идёт на сервер. Значит он делается
`ui.remote` (источник 3, раздел 4) **без QuickJS вообще** — модуль собирает разметку на сервере теми
же функциями `@superizer/ui`. Рантайм скриптов понадобится, если захочется локального черновика
порядка или массовых переносов. Рекомендация — Q7.

**Где.** Ветки `js-module` в двух репозиториях: `/prj/restoapp-jsmod` (клиент) и
`/prj/restoapp-dev-jsmod` (сервер); в клиенте симлинк `restoapp-dev -> ../restoapp-dev-jsmod`, и
тесты берут сервер **своего** workspace (`protocol/build.gradle.kts`, `composeApp/build.gradle.kts`:
`restoapp-dev` в корне проекта раньше, чем `../restoapp-dev`). `node_modules` и `local_modules` —
симлинками на главный чекаут, поэтому `git status` сервера показывает две строки `T local_modules/*`;
так и задумано, коммитить их не надо. Модуль поставлен с Marketplace:
`npx -y @webresto/cli@0.2.0 install simple-navigation -c staging` (1.7.1; в канале `main` только
1.6.1, без админ-страницы), `WEBRESTO_LICENSE=null` — модуль бесплатный, `modules/*` в gitignore.
Стенд видит модуль только если в корне сервера есть `.sailsrc` (копия `.sailsrc.default`):
`paths.hooks: "modules"` — без него Sails хуки модулей не грузит, и `/admin/navigation-manager` — 404.

**Что внутри модуля** (`simple-navigation` 1.7.1, образец для нас): модель `Navigation` — меню с
`mnemonicId` и списком пунктов в JSON-поле `navigation_menu`; админ-часть — приложение adminizer
(`src/adminizer/NavigationApp.ts`): токен `navigation-manager`, четыре JSON-роута и страница, чей
исходник `ui/NavigationManager.jsx` собирается esbuild-ом в `assets/adminizer/NavigationManager.js`,
а панель импортирует этот файл по URL от `ctx.asset()`. React и компоненты — глобали панели
(`window.React`, `window.UIComponents`), в бандл не входят. Ровно эта схема и перенесена на мобильное.

**Как отдаётся.** Приложение регистрируется с `script: {file}` — путём к собранному бандлу; хук
читает и хеширует его (`lib/scripts.ts`), а декларация несёт `script: {url, sha256, size, min}`, где
`url` — `/api/mobile/app-assets/<app>/<sha256>.js`. Хеш в имени: новая сборка — новая ссылка, кеш
можно держать вечно, чужой хеш — 404, а не старый файл. Хеш входит в отпечаток реестра, то есть в
ревизию декларации, поэтому после выкатки клиент сам перечитывает `describe`. Файла нет или он пуст —
сервер падает при старте, а не телефон потом.

**Сборка на живом сервере.** На каждую декларацию файл осматривается заново (`rereadScript`): size и
mtime против прочитанного в прошлый раз, изменился — хешируется снова. Поэтому `npm run build:mobile`
в модуле или обновление модуля на сервере доходят до клиентов без лифта: хеш сдвинулся, ревизия за
ним, клиент перечитал `describe` и скачал новый код; ссылка прошлой сборки отдаёт 404. Файл, застигнутый
недописанным или удалённый, остаётся прежним: отпечаток снимается ещё раз после чтения тела, и
сдвинувшийся файл берётся на следующем осмотре, а не отдаётся битым. Открытый в этот момент экран
доживает на старом коде до переоткрытия — новый бандл к тому времени уже скачан.

**Модули сервера — в декларации.** `modules: [{id, version, kind, title, app?, script?}]`:
`system` — из `MM_SYSTEM_MODULES` (`@webresto/core`, graphql), `installed` — то, что загрузил
менеджер модулей (`app-manager-proto.getModules()`). Модуль, принёсший приложение, назван в `app` и
несёт ту же ссылку в `script` — но только если человеку это приложение доступно.

**Приложение.** Живёт в самом модуле (`simple-navigation` 1.8.0): `src/mobile/NavigationMobileApp.ts`
+ `mobile/navigation.js` → `assets/mobile/navigation.js`, права — его же токен `navigation-manager`,
методы `navigation.menus / menu / create / save / remove`. Модуль регистрирует его сам, на событии
`mobile-api:ready` — оно для этого и было; в хуке о «Навигации» не осталось ничего.

**Клиент.** `ScriptRef` и `ServerModule` в `:protocol`; `MobileApi.script(token, ref)` качает по
ссылке **только своего** сервера и проверяет размер и sha256 (`sha256Hex` — SHA-256 в commonMain, без

и откат на него, если скачать не удалось; `min` больше протокола клиента — не качаем вовсе.
`ServerSession` держит кеш в хранилище сервера (`script-<sha256>.js`) и начинает качать сразу, как
декларация назвала скрипт.

**Тесты.** Сервер: `tests/mobile-api.scripts.test.ts`, 11 штук на приложении-фикстуре — ссылка и хеш в

ревизию, пересборка на живом сервере подхватывается (а недописанный файл — нет), отказ регистрации

  универсальному рендеру тяжелее всего. Альтернатива — после первого релиза целиком (срезы 1–3).
- **Q2. Кто пишет скрипты.** Рекомендую: только модули RestoApp на сервере — тогда подписи и
  отдельной проверки кода не нужно. Если скрипты будут присылать сторонние модули или чужой CDN —
  подпись автора и список доверенных ключей.
- **Q3. Универсальный рендер — в Kotlin или разметкой с сервера.** Решить после этапа 4: если
  скрипты прижились, подсказки `ui` методов и автоэкраны слоя данных сервер может превращать в
  разметку сам, и у клиента останется один рендер.
- **Q4. Нужно ли это Unitool.** От ответа зависит только, насколько общим делать `ScriptService`;
  модуль в Superizer нужен в любом случае (D4).
- **Q5.** Закрыт: `@superizer/ui` живёт в репозитории Superizer и публикуется в npm с той же версией,
  что Superizer.
- **Q6.** Закрыт: разметка с сервера нужна — и готовая в скрипте, и на каждый запрос. Формат допускает
  её с первого дня; делается этапом 5, с первым экраном, которому не нужна логика на устройстве.
- **Q7. Редактор каталогов — разметкой с сервера или скриптом.** Рекомендую разметкой (`ui.remote`,
  этап 5): логики на устройстве у редактора нет, QuickJS для него не нужен, и он выходит раньше
  ядра скриптов. Скриптом — если нужен локальный черновик порядка.
- **Q8. Что такое навигация на этом сервере.** Сейчас `navigation` в `config/adminpanel.js` пустой, и
  править нечего. Включаем разделы и элементы (какие модели идут в меню сайта ссылками)? Или первый
  каталог в приложении — «Товары», где данные есть уже сегодня, а навигация за ним?
- **Q9. Перенос ветки на телефоне.** Рекомендую «Переместить в…» (выбор родителя и места), без
  таскания; таскание — на планшете, если понадобится.
